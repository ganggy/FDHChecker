# คู่มือ FDH Checker ทั้งระบบ

ฉบับผู้ใช้งาน ผู้ดูแลระบบ และผู้ติดตั้ง • ตรวจเทียบโค้ดวันที่ 22 กันยายน 2569

เอกสารนี้อธิบายระบบตามโค้ด branch `main` commit `abdfa5f` เวอร์ชันแพ็กเกจ `1.0.1` ที่ตรวจในวันจัดทำ ครอบคลุมเมนูที่ประกาศใน `src/config/menuDefinitions.ts` และหน้าตั้งค่าระบบ หากเครื่องโรงพยาบาลใช้คนละ commit ให้ตรวจชื่อเมนูและการตั้งค่าจริงประกอบ ไม่ใช้ IP ของโรงพยาบาลต้นแบบเป็นค่าติดตั้งของทุกแห่ง

คู่มือนี้เป็นวิธีใช้โปรแกรมและตรวจข้อมูล ไม่ใช่ประกาศหลักเกณฑ์จ่ายเงินฉบับใหม่ ผล “ผ่าน” หมายถึงผ่านการตรวจที่โปรแกรมรองรับ ไม่ใช่คำยืนยันว่าจะได้รับเงิน เงื่อนไขคัดกรองและ ANC ที่อธิบายเป็นพฤติกรรมของโค้ดที่ตรวจ ไม่ใช่การรับรองหลักเกณฑ์ผู้จ่ายปัจจุบัน

## 1. ภาพรวมและลำดับงานทั้งระบบ

FDH Checker อ่านข้อมูลการรับบริการจาก HOSxP เพื่อช่วยตรวจความครบถ้วน เตรียมส่งเคลม ติดตามผลตอบกลับ และกระทบยอดลูกหนี้ ฐานข้อมูลแอปเก็บบัญชีผู้ใช้ การตั้งค่า ผลนำเข้า และประวัติงานแยกจากข้อมูลบริการต้นทาง

ลำดับงานที่แนะนำ:

1. IT ตั้งค่าฐานข้อมูล โรงพยาบาล ขอบเขตพื้นที่ รหัสสิทธิ์ และบัญชีผู้ใช้
2. OPD/IPD ตรวจรายการและเปิดรายละเอียดรายครั้ง แก้ข้อผิดพลาดในระบบต้นทาง
3. เจ้าหน้าที่กองทุนตรวจหลักฐานบริการและช่องทางเบิกของแต่ละรายการ
4. งานเคลมตรวจความพร้อม 16 แฟ้ม เลือกรายการ และส่งตามช่องทางที่กำหนด
5. ดึงสถานะ FDH และนำเข้า ClaimDetail/REP/STM/INV ตามรอบที่ได้รับ
6. ติดตาม Reject/C/Deny จัดคิวผู้รับผิดชอบ แก้และตรวจซ้ำก่อนส่งใหม่
7. การเงินกระทบยอดและจัดชุดลูกหนี้ หัวหน้างานตรวจรายงานสรุป
8. IT สำรองข้อมูล ตรวจบริการ และอัปเดตตามแผน

## 2. เข้าใช้งาน บัญชี และสิทธิ์

### เข้าระบบและเปลี่ยนรหัสผ่าน

1. เปิด URL ที่ IT ของโรงพยาบาลแจ้ง ตรวจชื่อหน่วยบริการบนหน้าเว็บ
2. กรอกบัญชีของตนเองและเข้าสู่ระบบ หาก session หมดอายุ ให้เข้าใหม่ก่อนทำรายการต่อ
3. ตรวจว่ามีเมนูตามหน้าที่ หากไม่มี ให้แจ้งผู้ดูแลตรวจกลุ่มและสิทธิ์เมนู
4. ใช้ปุ่มเปลี่ยนรหัสผ่านของระบบ กรอกรหัสเดิม รหัสใหม่ และยืนยันให้ตรงกัน
5. โค้ดกำหนดรหัสใหม่อย่างน้อย 12 ตัวอักษร หลังเปลี่ยนสำเร็จต้องเข้าสู่ระบบใหม่
6. ออกจากระบบเมื่อสิ้นสุดงาน โดยเฉพาะเครื่องใช้ร่วมกัน

### แบ่งหน้าที่ใช้งาน

| ผู้รับผิดชอบ | งานหลัก | ผลงานที่ส่งต่อ |
| --- | --- | --- |
| IT/ผู้ดูแลระบบ | เชื่อมต่อ ติดตั้ง สมาชิก สำรอง อัปเดต | ระบบพร้อมใช้และค่ารายไซต์ที่ตรวจแล้ว |
| เวชระเบียน OPD/IPD | ตรวจ Dx หัตถการ ยา สิทธิ์ และข้อมูลรับบริการ | รายการพร้อมตรวจเคลม/รายการรอแก้พร้อมเหตุผล |
| เจ้าหน้าที่กองทุน | ตรวจหลักฐานบริการ เงื่อนไข และ mapping | รายการที่ผ่านการทบทวนตามกองทุน |
| งานเคลม | ตรวจแฟ้ม ส่ง ติดตามสถานะ นำเข้าผล | เลขอ้างอิงและสถานะตอบกลับ |
| การเงิน/บัญชี | REP/STM ลูกหนี้ กระทบยอด | ชุดบัญชีและผลต่างที่อธิบายได้ |
| หัวหน้างาน | ตรวจภาพรวม จัดผู้รับผิดชอบ | ข้อสรุปพร้อมรายการติดตาม |

`ตั้งค่าระบบ`, `จัดการฐานข้อมูล REP/STM` และ `สมาชิกและสิทธิ์เมนู` เป็นหน้าสำหรับผู้ดูแลตามโค้ด ส่วนเมนูอื่นขึ้นกับสิทธิ์ที่กำหนด การเห็นเมนูไม่ได้แทนสิทธิ์ฐานข้อมูลหรือสิทธิ์บัญชีที่ระบบผู้จ่าย

## 3. เตรียมติดตั้งที่โรงพยาบาลใหม่

### แบบบันทึกก่อนติดตั้ง

| รายการ | สิ่งที่ต้องยืนยัน |
| --- | --- |
| เครื่องแอป | hostname/IP, OS, ผู้รับผิดชอบ, เวลาเครื่อง และพื้นที่ว่าง |
| บัญชีบริการ | Linux user ที่รัน FDH และ PM2 ใช้บัญชีเดียวตลอด |
| Repository | URL, branch ที่อนุมัติใช้, commit เริ่มต้น |
| HOSxP | ชนิดฐาน host/port/database/schema และสิทธิ์บัญชี |
| ฐานแอป | MySQL/MariaDB ของ REPSTM และนโยบายสำรอง |
| URL ผู้ใช้ | ชื่อโดเมน HTTPS, certificate, CORS, reverse proxy |
| เครือข่าย | เส้นทางไปฐานข้อมูล DNS GitHub npm และบริการผู้จ่ายที่ใช้ |
| หน่วยบริการ | HCODE ชื่อโรงพยาบาล สิทธิ์ WALKIN icode และพื้นที่รับผิดชอบ |
| บริการเดิม | PM2/systemd/Nginx ที่มีอยู่ พอร์ตที่ถูกใช้ และแผนย้อนกลับ |

ก่อนติดตั้งบนเครื่องที่มีระบบเดิม ให้สำรวจ service ก่อน ไม่รัน backend สองตัวแย่งพอร์ตเดียวกัน PM2 ของ `root` กับบัญชีบริการเป็นคนละชุด แม้ใช้คำสั่งชื่อเดียวกัน

```bash
id -un
cat /etc/os-release
node -v
npm -v
git --version
df -h /opt
free -h
systemctl list-units --type=service --all --no-pager | grep -Ei 'fdh|pm2'
ss -ltnp | grep -E ':3506|:3507'
timeout 5 getent ahostsv4 github.com
curl -I --max-time 10 https://github.com
curl -I --max-time 10 https://registry.npmjs.org
```

### ลำดับติดตั้ง

1. เตรียม Node.js 22, npm, Git, Bash, curl และ GNU timeout ตามมาตรฐานแพ็กเกจของโรงพยาบาล ติดตั้ง PM2 ให้บัญชีบริการเรียกใช้ได้ หากเลือกใช้ Nginx ให้เตรียม certificate และ config ก่อนเปิดให้ผู้ใช้เข้า
2. ให้ผู้ดูแลระบบสร้าง `/opt/FDHChecker` และสิทธิ์ของบัญชีบริการ โค้ด PM2 รุ่นที่ตรวจยังระบุ path นี้ตายตัว หากใช้ path อื่นต้องปรับทั้ง PM2, updater, backup และ Nginx ให้ตรงกัน
3. clone repository และเลือก branch ที่ใช้งานจริง ตัวอย่างชุดปัจจุบันใช้ `main`; ไม่สลับข้าม branch เพียงเพื่อแก้อัปเดตค้าง
4. สร้างฐาน REPSTM และบัญชีผ่าน DBA ก่อนเริ่มแอป ตรวจสิทธิ์สร้าง/ปรับตารางแอปตามขั้นตอนเริ่มระบบ ส่วน HOSxP ใช้สิทธิ์อ่านเป็นหลัก และเปิดสิทธิ์เขียนเฉพาะงานที่โรงพยาบาลอนุมัติ
5. สร้าง `.env` และแทนค่าตัวอย่างทุกจุดด้วยข้อมูลไซต์ตามบท 4 อย่าใช้ host/user/password จากไฟล์ตัวอย่างโดยไม่ตรวจ
6. ติดตั้ง dependency รวม devDependencies เพราะเซิร์ฟเวอร์ต้องใช้ทดสอบและ build
7. ตรวจโค้ดและ build ให้ผ่านก่อนเริ่ม PM2 หยุดเมื่อคำสั่งใดล้มเหลว

```bash
git clone --branch main https://github.com/ganggy/FDHChecker.git /opt/FDHChecker
cd /opt/FDHChecker
cp .env.example .env
chmod 600 .env
# แก้ .env ตามบท 4 ก่อนรันต่อ
npm ci --include=dev
npm run check
npm run build:all
```

8. สร้าง `/var/log/fdh-checker` ให้บัญชีบริการเขียนได้ เพราะ ecosystem ปัจจุบันเขียน log ที่นี่ แล้วเริ่มบริการด้วยบัญชีเดียวกัน

```bash
sudo install -d -o "$(id -un)" -g "$(id -gn)" /var/log/fdh-checker
pm2 start deploy/pm2/ecosystem.config.cjs
pm2 status
curl --fail --max-time 10 http://127.0.0.1:3506/api/live
curl --fail --max-time 10 http://127.0.0.1:3506/api/ready
curl --fail --max-time 10 http://127.0.0.1:3507/
pm2 save
pm2 startup
```

9. รันคำสั่งสิทธิ์สูงที่ `pm2 startup` แสดงสำหรับบัญชีบริการ ตรวจ service หลัง reboot ในเวลาที่กำหนด การที่ `pm2 status` ขึ้น online ยังไม่แทนการผ่าน `/api/ready`
10. ตั้ง Nginx ตาม `deploy/nginx/fdh-checker.conf` โดยเปลี่ยน hostname/path/certificate และตรวจ `nginx -t` ก่อน reload ทดสอบหน้า login และ `/api/ready` จาก URL ของผู้ใช้จริง
11. สร้างผู้ดูแลครั้งแรกตามบท 4 ตั้งค่ารายโรงพยาบาลตามบท 5 และทำรายการตรวจรับบท 29

ไฟล์ ecosystem ปัจจุบันมี `fdh-backend` รัน bundle และ `fdh-frontend` รัน Vite preview ที่ 3507 การใช้ Nginx serve `dist` โดยตรงเป็นอีก topology หนึ่ง หากเลือกแบบนั้นต้องกำหนด `FDH_PM2_APPS` ให้ตรง process ที่มีจริง และทดสอบ updater ด้วย topology นั้น

## 4. ตั้งค่า environment และฐานข้อมูล

แก้ `.env` บนเซิร์ฟเวอร์ ไม่ commit รหัสผ่านหรือ token ลง Git ใช้ไฟล์สิทธิ์ 600 และให้เจ้าของบริการอ่านได้ โค้ดที่อ่านค่าจริงมีน้ำหนักเหนือคอมเมนต์ในไฟล์ตัวอย่าง

| กลุ่ม | ตัวแปร/ค่า | วิธีใช้ |
| --- | --- | --- |
| HOSxP | `HOSXP_DB_TYPE=mysql` หรือ `postgresql` | ใช้ชื่อนี้ตาม `hospitalDatabaseConfig.ts`; ไม่ใช้ `HOSXP_DIALECT` แทน |
| การเชื่อม HOSxP | `HOSXP_HOST`, `HOSXP_PORT`, `HOSXP_DB`, `HOSXP_USER`, `HOSXP_PASSWORD` | ให้ตรงฐานและบัญชีของไซต์ |
| PostgreSQL | `HOSXP_SCHEMA`, `HOSXP_SSL` | ยืนยัน schema/SSL กับ DBA; การเชื่อม HIS แบบนี้อ่านอย่างเดียว |
| ฐานแอป | `REPSTM_HOST`, `REPSTM_PORT`, `REPSTM_DB`, `REPSTM_USER`, `REPSTM_PASSWORD` | แยกจาก HIS ตามโครงสร้างที่โรงพยาบาลเตรียม |
| API | `PORT=3506`, `NODE_ENV=production` | หากเปลี่ยนพอร์ตต้องปรับ PM2/proxy/health URL ด้วย |
| CORS | `CORS_ORIGINS` | ใช้ชื่อนี้ตาม `server/index.ts`; ใส่ origin ที่อนุญาตคั่นด้วยจุลภาค |
| Bootstrap admin | `APP_BOOTSTRAP_ADMIN_USERNAME`, `APP_BOOTSTRAP_ADMIN_PASSWORD` | ใช้ครั้งแรกเมื่อไม่มี active admin; รหัสผ่านอย่างน้อย 12 ตัว |
| Self-update | `FDH_SELF_UPDATE_ENABLED`, `FDH_APP_DIR`, `FDH_DEPLOY_BRANCH` | เปิดเมื่อเตรียมบริการและ branch ตรงกันแล้ว |
| รีสตาร์ต updater | `FDH_PM2_APPS`, `FDH_HEALTH_BASE_URL` | ชื่อ process จริงและ API ภายในเครื่อง |
| AI เสริม | `OLLAMA_BASE_URL`, `OLLAMA_MODEL`, `OLLAMA_EMBED_MODEL` | ตั้งเมื่อจะใช้ Local AI; ไม่ต้องเปิดเพื่อทำ OPD/IPD พื้นฐาน |

### ผู้ดูแลครั้งแรก

1. ให้ DBA เตรียมฐานแอปและสิทธิ์ให้พร้อม
2. ตั้งตัวแปร bootstrap ชั่วคราวใน `.env` ใช้รหัสผ่านใหม่ที่ผู้ดูแลกำหนดเอง
3. เริ่ม backend และตรวจ log ว่าสร้าง admin สำเร็จ หากมี active admin อยู่แล้วไม่ใช้วิธีนี้เพื่อแทนบัญชีเดิม
4. เข้าสู่ระบบด้วยบัญชีที่สร้าง ตรวจเมนูตั้งค่าและสมาชิก
5. ลบตัวแปร bootstrap ออกจาก `.env` แล้วรีสตาร์ตเฉพาะ backend ตามแผน
6. สร้างบัญชีใช้งานรายคนและแบ่งกลุ่มต่อ ห้ามเผยแพร่ `.env` ใน ticket

### การตั้งค่าผ่านหน้าเว็บ

เปิด **ตั้งค่าระบบ → ฐานข้อมูล HOSxP** เลือกชนิดฐาน กรอกค่าที่ DBA ยืนยัน ทดสอบก่อนบันทึก และรีสตาร์ต backend เมื่อระบบแจ้ง การตั้งค่าที่บันทึกอาจใช้ไฟล์ override ใน `.secrets`; การแก้ `.env` อย่างเดียวจึงต้องตรวจด้วยว่ามี override อยู่หรือไม่ ดูรายละเอียดใน `deploy/HOSPITAL_DATABASE.md`

PostgreSQL ไม่รองรับงานเขียนกลับ HOSxP ในระบบนี้ ปุ่มเติมข้อมูลหรือเพิ่มรายการที่ต้องเขียนอาจถูกปฏิเสธ ให้ดำเนินการใน HIS ด้วยผู้มีสิทธิ์แล้วตรวจซ้ำ

## 5. ตั้งค่ารายโรงพยาบาลและกฎระบบ

### ขอบเขตบริการ / WALKIN

1. เข้าด้วย admin เปิด **ตั้งค่าระบบ → ขอบเขตบริการ / WALKIN**
2. ตรวจชื่อและ HCODE ที่อ่านจาก `opdconfig` หากยังเป็นชื่อโรงพยาบาลอื่น ให้ตรวจฐานที่เชื่อมก่อนแก้ข้อความบนเว็บ
3. เลือกสิทธิ์ UC WALKIN จาก `pttype` ของไซต์ เช่นรหัส 40/41 และ 50/51 เป็นเพียงตัวอย่างที่ต่างไซต์กัน ไม่ควรคัดลอกข้ามโรงพยาบาล
4. ระบุ `icode` ของรายการ WALKIN ที่ใช้จริง
5. เลือกหมู่บ้านในเขตรับผิดชอบจาก `village` ตรวจทั้งชื่อและ `village_id`
6. บันทึก แล้วกลับไปตรวจ WALKIN ใหม่และทดสอบรายงาน PCU ด้วยข้อมูลตัวอย่าง
7. บันทึกวันที่ ผู้ตั้งค่า และผู้ยืนยันข้อมูลพื้นที่ไว้ในทะเบียนภายใน

### แท็บตั้งค่าอื่น

## 6. วิธีอ่านตารางและทำงานประจำวัน

เลือกวันให้ตรงความหมายของแต่ละหน้า เช่นวันรับบริการ วันจำหน่าย หรืองวดไฟล์ กดดึง/ค้นหาหลังเปลี่ยนตัวกรอง แล้วตรวจจำนวนรายการและช่วงวันที่บนผลลัพธ์เสมอ การค้นหาตารางบางหน้าเป็นการกรองข้อมูลที่ดึงมาแล้ว ไม่ใช่ค้นทั้งฐาน

### เริ่มวัน

1. ตรวจโรงพยาบาลและบัญชีที่ใช้งาน
2. ดึง OPD/IPD ของรอบที่รับผิดชอบ เริ่มช่วงสั้นเมื่อข้อมูลมาก
3. เปิดตัวอย่างอย่างน้อยหนึ่ง VN และหนึ่ง AN ตรวจ Dx ยา หัตถการ และสิทธิ์
4. แยกรายการรอแก้ตามแผนกผ่านคิวงาน
5. ตรวจรายการใหม่ของกองทุนและรายการตอบกลับจากรอบก่อน

### จบวัน

1. เทียบจำนวนรายการที่ตรวจ พร้อมส่ง ส่ง และรอแก้
2. เก็บเลขอ้างอิงการส่งและไฟล์ผลตอบกลับตามรอบ
3. อัปเดตผู้รับผิดชอบและหมายเหตุของงานค้าง
4. ส่งต่อผลต่างพร้อม VN/AN และเหตุผลผ่านช่องทางที่ได้รับอนุญาต
5. ออกจากระบบและเก็บไฟล์ส่งออกในพื้นที่ควบคุมสิทธิ์

ตัวเลข “จำนวนคน”, “จำนวนครั้ง”, “จำนวนรายการบริการ” และ “จำนวนแถว REP” ไม่จำเป็นต้องเท่ากัน ห้ามรวมยอดข้ามหน่วยนับโดยไม่ตรวจรายการต้นทาง

## 7. รายการ OPD และรายละเอียดรายครั้ง

**ผู้ใช้หลัก:** เวชระเบียน OPD งานประกัน และเจ้าหน้าที่กองทุน • **เมนู:** รายการ OPD

1. เลือกช่วงวันที่และกองทุน/ตัวกรองที่หน้าแสดง แล้วดึงข้อมูล
2. ตรวจ HN, VN, วันบริการ สิทธิ์ และสถานะความครบถ้วน
3. เปิดรายการรายคน/ราย visit ตรวจว่า VN ตรงกับรายการที่เลือก ไม่ใช้ HN เพียงอย่างเดียวแยกหลาย visit
4. อ่านการวินิจฉัยหลัก/ร่วม รายการยา ใบสั่งยา Lab และหัตถการที่ระบบอ่านได้
5. เมื่อมีคำเตือน ให้จดข้อความและแหล่งข้อมูล ไม่เติม diagnosis เพียงเพื่อให้แถบผ่าน
6. แก้ใน HOSxP โดยเจ้าหน้าที่ที่รับผิดชอบ แล้วดึงรายการใหม่
7. ส่งต่อไปตรวจความพร้อมหรือกองทุนที่เกี่ยวข้องเมื่อข้อมูลครบ

**ผลที่ควรได้:** ข้อมูลราย visit ตรงกับ HOSxP และรายการผิดปกติมีเจ้าของงาน ไม่ใช่เพียงยอดสรุปเป็นสีเขียว

**Diag หน้าหลักมีแต่รายละเอียดว่าง:** ตรวจ VN/AN และข้อความแหล่งข้อมูล ระบบอาจอ่านรหัสสรุปจาก `vn_stat/an_stat` เมื่อแถวรายละเอียดไม่พบ ให้ IT ตรวจ adapter/schema หากมีคำเตือนแหล่งหัตถการ ไม่ตีความว่าทั้ง visit ไม่มีการรักษา

**ใบสั่งยาว่าง:** ตรวจ `opitemrece` ของ VN นั้น ชื่อรายการและ mapping ที่มีจริง รายการราคา 0 ยังเป็นรายการบริการได้ ไม่ควรถูกใช้เป็นเหตุสรุปว่าไม่ได้จ่ายยา

## 8. ส่งออก OPD 16 แฟ้ม

**เมนู:** ส่งออก OPD • **ก่อนเริ่ม:** ตั้งค่า FDH สิทธิ์ และข้อมูลโรงพยาบาลเรียบร้อย

1. กำหนดช่วงวันที่และสิทธิ์ที่ต้องการส่ง ตรวจว่าเป็นรอบ OPD
2. ดึงรายการและตรวจเงื่อนไขที่หน้าจอใช้คัดผู้ป่วย
3. ค้นด้วย VN/HN หากต้องการตรวจรายเฉพาะ และเปิดรายละเอียดเคสที่มีคำเตือน
4. ตรวจข้อมูลประจำตัว สิทธิ์ Dx หัตถการ รหัสบริการ ยอด และข้อมูลประกอบการส่ง
5. ใช้หน้าตรวจความพร้อม 16 แฟ้มช่วยแยกปัญหาตามแฟ้มก่อนส่ง
6. เลือกเฉพาะรายการที่เจ้าหน้าที่ตรวจแล้ว อ่านจำนวนรายการในข้อความยืนยัน
7. แยกการดาวน์โหลดไฟล์ออกจากการกดส่ง FDH การมีไฟล์ในเครื่องยังไม่แปลว่าส่งสำเร็จ
8. หากใช้คำสั่งส่งจริง ตรวจปลายทางและรอบงานก่อนยืนยัน รอผลรายรายการและบันทึกเลขอ้างอิง
9. ไปดึงสถานะเคลมหลังส่งตามรอบที่เหมาะสม และติดตาม REP ภายหลัง

หากการเชื่อมต่อขาดระหว่างส่ง ให้ตรวจเลขอ้างอิงหรือสถานะฝั่ง FDH ก่อนกดส่งซ้ำ หากหน้าจอเปิดให้ใส่ FCode ให้ใช้รหัสที่ตรวจจากข้อมูลจริง ไม่ใช้ค่าทดแทนเพื่อให้ผ่าน validation

## 9. รายการ IPD และ Pre-audit

**เมนู:** รายการ IPD • **ผู้รับผิดชอบ:** เวชระเบียน IPD และผู้ทบทวนชาร์ต

1. ตั้งช่วงวันและตัวกรองตามหน้า ตรวจว่าคัดด้วยวันใดก่อนเทียบรายงานอื่น
2. ตรวจ AN/HN วอร์ด วันรับเข้า วันจำหน่าย และสถานะจำหน่าย
3. เปิดชาร์ตรายตัว ตรวจ principal diagnosis, diagnosis ร่วม, procedure, ยา และค่าใช้จ่าย
4. อ่านคำเตือน IPD Pre-audit พร้อมหลักฐานจากเวชระเบียน
5. เปิดรายละเอียดกฎที่หน้าแสดงเพื่อดูเหตุผล เช่นความสัมพันธ์ Dx/Procedure อายุ เพศ หรือวันนอน
6. ส่งประเด็นให้ผู้รับผิดชอบเวชระเบียน/ผู้รักษายืนยัน ไม่แก้โรคตามผลอัตโนมัติโดยไม่มีหลักฐาน
7. แก้ข้อมูลใน HIS ดึงใหม่ และตรวจ AN เดิมซ้ำ

**ผ่านกฎอัตโนมัติ** ไม่แทนการตรวจคุณภาพเวชระเบียนทั้งหมด ส่วน **ต้องทบทวน** ไม่ได้แปลว่าคนไข้ไม่เข้าเกณฑ์แน่นอน ต้องเปิดหลักฐานและบันทึกข้อสรุป

หากรายการยา/หัตถการไม่ขึ้น ให้ตรวจว่าผูกด้วย AN และตรวจตารางที่ HIS รุ่นนั้นใช้ ข้อมูลรายคนควรตรวจแยกจากยอดสรุป เพราะแหล่งข้อมูลอาจต่างกัน

## 10. ส่งออก IPD และมอนิเตอร์เคลม IPD

### ส่งออก IPD

1. เปิด **ส่งออก IPD** เลือกรอบและดึงข้อมูล
2. ตรวจ AN วันรับ/จำหน่าย สิทธิ์ Dx/Procedure และผล Pre-audit
3. เลือกรายการที่ผ่านการตรวจชาร์ต อ่านจำนวนและรายละเอียดก่อนยืนยัน
4. ส่งออกชุด 16 แฟ้มหรือดำเนินการส่งตามปุ่มที่หน้าเปิดให้ใช้
5. เก็บผลตอบรับและเลขอ้างอิงแยกรอบส่ง จากนั้นติดตามในมอนิเตอร์

### มอนิเตอร์เคลม IPD

1. เปิด **มอนิเตอร์เคลม IPD** กำหนดช่วงและค้น AN/HN/ชื่อ/REP
2. กรองสถานะปัจจุบัน สิทธิ HIPDATA วอร์ด หรือผล IPD Pre-audit
3. เปิดรายการที่ค้างเพื่อดูว่าติดขั้นเตรียมข้อมูล ส่ง ผลตอบกลับ หรือรอข้อมูลการเงิน
4. เทียบเลขอ้างอิงกับ REP/STM ที่นำเข้า หากไม่พบให้ตรวจงวดไฟล์และวันจำหน่าย
5. จัดผู้รับผิดชอบแต่ละ AN และติดตามจนมีผลที่ตรวจสอบย้อนกลับได้

ผลที่ควรได้คือเห็นตำแหน่งงานค้างของ AN พร้อมหลักฐาน ไม่ใช้ยอดทั้งหมดในมอนิเตอร์แทนยอดเงินรับจริง

## 11. ตรวจความพร้อม 16 แฟ้มและคิวงานส่งตรวจ

### ตรวจความพร้อม 16 แฟ้ม

เมนู **นำเข้า/ตรวจสิทธิ → ตรวจความพร้อม 16 แฟ้ม** ใช้แสดงปัญหาก่อนส่งโดยจัดตามแฟ้ม

1. ตั้งรอบข้อมูลและดึงรายการที่ต้องตรวจ
2. อ่านผลรวมก่อน แล้วเปิดรายละเอียดปัญหาตามแฟ้ม
3. ตรวจตัวระบุผู้ป่วย สิทธิ์ การวินิจฉัย หัตถการ และยอดที่เกี่ยวข้องกับคำเตือน
4. ส่งต่อรายการที่ต้องแก้ พร้อมชื่อแฟ้ม/ข้อความตรวจและ VN
5. แก้ข้อมูลต้นทางและรันใหม่ด้วยช่วงเดิม
6. นำรายการที่พร้อมเข้าสู่กระบวนการส่ง ไม่ถือว่าการตรวจหน้านี้ได้ส่ง FDH แล้ว

### คิวงานส่งตรวจ

เปิด **ติดตามผลเคลม → คิวงานส่งตรวจ** เลือกรอบ/สถานะและค้นรายการ จากนั้นเปิดแก้ไขสถานะ ระบุผู้รับผิดชอบและหมายเหตุ แล้วบันทึก

| สถานะในคิว | งานถัดไป |
| --- | --- |
| รอแก้เวชระเบียน | ส่งให้ผู้รับผิดชอบชาร์ตตรวจหลักฐาน |
| รอ Authen Code | ตรวจระบบ Authen และการจับคู่ visit |
| รอ ICD/ICD9 | ตรวจ coding จากเวชระเบียน |
| รอการเงิน | ตรวจรายการราคา/สิทธิ์และรหัสบัญชี |
| พร้อมส่ง | ตรวจรอบและเลือกส่งในหน้าส่งออก |
| ส่งแล้ว | ตรวจผลตอบรับและเลขอ้างอิง |
| ตีกลับ | บันทึกสาเหตุและติดตามแก้ก่อนส่งใหม่ |

การเปลี่ยนสถานะคิวเป็น “ส่งแล้ว” เป็นการบันทึกงาน ไม่ใช่หลักฐานว่าระบบผู้จ่ายรับรายการแล้ว ต้องมีเลขอ้างอิงหรือผลตอบกลับประกอบ

## 12. ดึงสถานะเคลม FDH และนำเข้า ClaimDetail

### ดึงสถานะเคลม FDH

1. เปิด **นำเข้า/ตรวจสิทธิ → ดึงสถานะเคลม FDH**
2. ตรวจสภาพแวดล้อม Production/UAT และ HCODE ที่อ่านมาอัตโนมัติ
3. ใช้บัญชีหรือ token ที่ได้รับสำหรับหน่วยบริการนั้น หลีกเลี่ยงส่ง token ในภาพหน้าจอ
4. กำหนดรายการ/ช่วงตามหน้า หากใช้ `transaction_uid` ให้ใส่แยกบรรทัดและตรวจเลขให้ครบ
5. เริ่มดึงสถานะ รอผล และตรวจรายการที่สำเร็จ/ผิดพลาดแยกกัน
6. ใช้ผลนี้ประกอบติดตามเคลม ส่วนยอดชดเชยต้องตรวจ REP/STM ต่อ

ถ้า token หมดอายุให้ยืนยันตัวตนใหม่ตามขั้นตอนของหน่วยงาน แล้วดึงเฉพาะรายการที่ยังต้องตรวจ การเปลี่ยน UAT เป็น Production ต้องตรวจเลขอ้างอิงของสภาพแวดล้อมนั้นด้วย

### รายละเอียดเคลม FDH

1. เปิด **รายละเอียดเคลม FDH** เลือกไฟล์ ClaimDetail `.xlsx` หรือ `.xls`
2. ตรวจ sheet/ข้อมูลตัวอย่างและรอบส่ง ระบุหมายเหตุให้แยกงวดได้
3. นำเข้าแล้วตรวจจำนวนรายการและข้อผิดพลาดที่รายงาน
4. เทียบ VN/AN/เลขอ้างอิงกับรายการส่งต้นทาง
5. เก็บไฟล์ต้นฉบับเพื่อค้นย้อนหลัง ไฟล์นี้เป็นรายละเอียดเคลม ไม่แทน STM หรือหลักฐานโอนเงิน

## 13. Authen สปสช. และปิดสิทธิ

### ตรวจสอบ Authen สปสช.

1. เปิด **นำเข้า/ตรวจสิทธิ → ตรวจสอบ Authen สปสช.** ซึ่งหน้าทำงานแสดงการนำเข้า Authen Code
2. ตรวจ Production/UAT และ token ที่ได้รับอนุญาต
3. ระบุรอบข้อมูลตามหน้า แล้วเริ่มตรวจ/นำเข้า
4. ตรวจจำนวนที่จับคู่ได้และรายการที่ไม่สำเร็จ แยกปัญหา token ออกจากปัญหาตัวระบุ visit
5. กลับไปตรวจรายการ OPD และคิวรอ Authen อีกครั้ง

### ปิดสิทธิ สปสช.

1. เปิด **ปิดสิทธิ สปสช.** ตรวจ token ผู้บันทึก และสภาพแวดล้อม
2. เลือกรอบ กรองสถานะต้องปิดสิทธิ/ปิดแล้ว/ยกเลิก/ผิดพลาด และสิทธิที่รองรับในหน้า
3. ตรวจ VN/HN/CID และชื่อให้ตรง visit จริง
4. เลือกเฉพาะรายการที่ได้รับมอบหมายแล้วดำเนินการปิดสิทธิ
5. ตรวจผลรายรายการและเก็บเหตุผลเมื่อไม่สำเร็จ
6. เมื่อ timeout ให้ตรวจสถานะก่อนส่งซ้ำ เพราะคำขออาจถึงปลายทางแล้ว

การปิดสิทธิเป็นการดำเนินการกับระบบภายนอก ต้องใช้ผู้รับผิดชอบที่มีสิทธิ์ ไม่ใช้เพื่อทดลองการติดตั้งบน Production และการปิดสิทธิสำเร็จยังไม่เท่ากับส่งเคลมหรือได้รับชดเชยสำเร็จ

## 14. นำเข้า REP / STM / INV

**เมนู:** นำเข้า/ตรวจสิทธิ → นำเข้า REP/STM • **รองรับในหน้าปัจจุบัน:** `.xlsx`, `.xls`, `.csv`, `.zip` และการเลือกโฟลเดอร์

1. รับไฟล์จากแหล่งที่เกี่ยวข้อง เก็บต้นฉบับแยกงวดและหน่วยบริการก่อนแก้ไขใด ๆ
2. เปิดหน้า นำเข้า REP/STM ระบุหมายเหตุ เช่น “รอบกันยายน ชุดทดสอบ”
3. เลือกไฟล์หรือโฟลเดอร์ รอระบบอ่านไฟล์และจัดคิว
4. ตรวจชนิด REP/STM/INV, sheet, จำนวนแถว และตัวอย่างข้อมูลของแต่ละรายการในคิว
5. หากจำแนกชนิดไม่ตรง ให้แก้ชนิดที่หน้าเปิดให้เลือกก่อนนำเข้า อย่านำเข้าจากชื่อไฟล์อย่างเดียว
6. ตรวจรายการซ้ำหรือไม่พร้อม แล้วนำเข้าเฉพาะรายการที่พร้อม
7. รอผลแต่ละไฟล์ ตรวจจำนวนที่สำเร็จ ข้าม และล้มเหลว
8. เปิดประวัตินำเข้าและดูข้อมูล batch เพื่อเทียบกับต้นฉบับ
9. ไป **กระทบยอด REP/STM** และ **รายการติด C / ปฏิเสธจ่าย** เพื่อตรวจผล

### นำเข้าซ้ำ

ปุ่มนำเข้าซ้ำมีการยืนยันและอาจแทนข้อมูล batch เดิม ต้องตรวจเหตุผลและเก็บต้นฉบับก่อน ไม่ใช้เพียงเพราะยอดรายงานยังไม่เปลี่ยนทันที ตรวจตัวกรองและการจับคู่ก่อน หากต้องลบ batch ให้ใช้บท 25

### ดาวน์โหลดจาก e-Claim ในหน้าเดียวกัน

ส่วน e-Claim มีขั้นเปิด browser/login เลือก ThaID ตามหน้าที่รองรับ ค้นรอบ เลือกรายการ และดาวน์โหลด ผู้ใช้ต้องดำเนินการยืนยันตัวตนเองก่อนเริ่มค้น หากไม่พร้อมใช้งานให้ตรวจ browser runtime/session ของเซิร์ฟเวอร์ หรือดาวน์โหลดไฟล์ด้วยช่องทางปกติแล้วนำเข้าไฟล์แทน

### ตรวจเมื่อยอดไม่ตรง

แยกจำนวนไฟล์ จำนวน sheet จำนวนแถว และจำนวน visit ออกจากกัน ตรวจงวด วันที่บริการ เลข REP/Statement/Tran ID และ HCODE ก่อนสรุปว่าข้อมูลหาย การไม่พบ STM อาจเกิดจากยังไม่ได้รับงวดนั้นหรือจับคู่ไม่สำเร็จ

## 15. ติดตาม Reject, C/Deny และ UUC1

### ติดตามเคส Reject

1. เปิด **ติดตามผลเคลม → ติดตามเคส Reject** กรองช่วงวันที่ สถานะ กองทุน หรือรหัสผิดพลาด
2. ค้น VN/HN/ชื่อ/TRAN_ID แล้วเปิดรายละเอียด
3. อ่าน error/verify code และหลักฐานต้นทางที่เกี่ยวข้อง
4. บันทึกสถานะ **รอดำเนินการ**, **กำลังดำเนินการ**, **ส่งใหม่แล้ว** หรือ **แก้ไขแล้ว** พร้อมผู้รับผิดชอบและหมายเหตุ
5. หลังแก้ข้อมูล ให้ตรวจซ้ำ ส่งตามช่องทางเดิม แล้วติดตามผลตอบรับใหม่
6. ไม่ปิดงานเพียงเพราะกด “ส่งใหม่แล้ว”; ต้องตรวจผลตอบกลับที่ยืนยันการแก้

### รายการติด C / ปฏิเสธจ่าย

1. เปิดเมนู กำหนดรอบและค้น code/VN/HN
2. อ่านคำอธิบายรหัสทั้งรหัสหลักและรหัสย่อย เช่น `C256-1` ไม่ตัดส่วนท้ายทิ้ง
3. เทียบคำอธิบายกับข้อมูลที่ถูกส่งจริงและ REP รอบนั้น
4. ส่งประเด็นให้ผู้รับผิดชอบพร้อมเลขอ้างอิงและบันทึกข้อสรุป
5. ถ้าคำอธิบายไม่มีหรือไม่ตรงรุ่น ให้ตรวจ catalog/เอกสารผู้จ่ายก่อนแก้ ไม่แปลรหัสจากการคาดเดา

### เคสบัตรทองรอเบิก (UUC1)

เลือก OPD/IPD/ทั้งหมด สิทธิ์และสถานะตามหน้า ค้น VN/HN/CID/REP แล้วตรวจลำดับ UUC1 ไป REP/STM แยก “ยังไม่ส่ง”, “ยังไม่พบไฟล์” และ “จับคู่ไม่ได้” ให้ชัดเจนก่อนจัดคิวติดตาม

คำอธิบาย C ที่มีอยู่ใน repository อ้าง catalog ที่นำเข้าไว้ ไม่รับรองว่าครอบคลุมประกาศภายหลังวันที่จัดทำทุกฉบับ

## 16. กองทุนเฉพาะและช่องทางเบิก

เมนู **กองทุนเฉพาะ** แยกมุมมอง **กองทุน FDH / e-Claim**, **กองทุน 43 แฟ้ม**, **กองทุน KTB / NTIP**, **กองทุนอื่นๆ** และ **รวมภาพรวมทุกกองทุน** มุมมองเหล่านี้ช่วยคัดรายการตามช่องทาง ไม่ได้ทำให้กองทุนทุกชนิดส่งผ่าน FDH ได้

### วิธีตรวจแต่ละกองทุน

1. เลือกมุมมองช่องทางที่ต้องใช้และช่วงวันที่
2. เลือกกองทุน อ่านเงื่อนไข/คำเตือนที่แสดงสำหรับกองทุนนั้น
3. ตรวจจำนวนและสถานะ แล้วเปิดรายละเอียด VN เพื่ออ่าน Dx ยา Lab หัตถการ และ ADP
4. แยก “มีหลักฐานแต่รหัสไม่ครบ” ออกจาก “ไม่มีหลักฐานว่ามีบริการ”
5. ส่งประเด็นให้ผู้รับผิดชอบตรวจเวชระเบียน และแก้เฉพาะข้อมูลที่มีหลักฐาน
6. ดึงข้อมูลใหม่หลังแก้ กดส่งเฉพาะช่องทางที่กองทุนนั้นรองรับ
7. เก็บเลขอ้างอิงและตามผลที่หน้าผลเคลมของช่องทางนั้น

### กลุ่มบริการและสิ่งที่ควรเปิดดู

| กลุ่ม | หลักฐานที่ควรตรวจในรายละเอียด |
| --- | --- |
| Palliative / เยี่ยมบ้าน | การวินิจฉัย บันทึกบริการจริง แผนดูแลและรหัสบริการ |
| Telemedicine / ส่งยา | ช่องทางบริการและรายการส่งยา ไม่ใช้ visit ปกติแทนหลักฐาน |
| สมุนไพร / ยาไทย | ชื่อยา รหัสยา จำนวน ราคา และความสัมพันธ์ Dx ที่โปรแกรมเตือน |
| ANC / Lab / Ultrasound / ทันตกรรม | visit ครรภ์ รหัสบริการ ผลตรวจ และการเชื่อมครรภ์ |
| หลังคลอด / วางแผนครอบครัว | วันที่บริการ Dx ยา/หัตถการและรายการประกอบ |
| คัดกรอง DM / หัวใจ / โลหิตจาง | ประวัติ Dx อายุ ผล Lab และรหัสคัดกรองตามกฎที่แสดง |
| HBV / HCV / ซิฟิลิส | ผลตรวจจริงและช่องทางบริการของรายการ |
| ยาพอกเข่า / งาน 43 แฟ้ม | Dx และหัตถการครบตามงาน 43 แฟ้ม |
| วัณโรคแฝง / KTB / VMI | เงื่อนไขและระบบปลายทางเฉพาะ ไม่ส่ง FDH แทนโดยอัตโนมัติ |
| ไต / ฟื้นฟู / อุปกรณ์ / บริการอื่น | หลักฐานและการอนุมัติเฉพาะที่รายการกำหนด |

### Auto Complete และปุ่มเพิ่มข้อมูล

ปุ่มบางกองทุนสามารถเขียนข้อมูลกลับ HIS ได้ ต้องอ่านรายการที่จะเพิ่ม จำนวน และข้อความยืนยันก่อนเสมอ ให้ผู้รับผิดชอบยืนยันว่ามีบริการจริงแล้ว หากไม่เข้าใจว่าจะเปลี่ยนตาราง/รายการใด ให้ตรวจรายละเอียดก่อนกด PostgreSQL เป็นแบบอ่านอย่างเดียวจึงไม่ควรคาดหวังว่าปุ่มเขียนจะทำงาน

### คัดกรองและ ANC ที่ตรวจข้าม visit

พฤติกรรมที่ตรวจในโค้ด: คัดกรองเบาหวานใช้ประวัติ E110-E119 และคัดกรองหัวใจหลอดเลือดใช้ I10/กลุ่ม I11/I120 ตามช่วงที่กำหนด โดยอ่านประวัติผู้ป่วยที่ HIS เชื่อมได้ทั้ง OPD/IPD ไม่จำกัดครั้งปัจจุบัน หากประวัติอ่านไม่ครบต้องทบทวนก่อนเบิก

ANC Ultrasound ตรวจการซ้ำภายในครรภ์ที่เชื่อมด้วย `person_anc_id` เมื่อหลาย visit/จำนวนรายการซ้ำ หรือระบุครรภ์ไม่ได้จะให้ตรวจเพิ่ม ไม่ใช้การนับวันแทนครรภ์จริง ข้อมูลนี้ไม่ครอบคลุมบริการนอกโรงพยาบาลที่ไม่มีในฐานที่เชื่อมต่อ

## 17. UC นอก CUP (WALKIN)

**เมนู:** การเงิน/ลูกหนี้ → UC นอก CUP (WALKIN)

1. ให้ admin ตั้งสิทธิ์และ icode ของโรงพยาบาลในบท 5 ก่อน
2. กำหนดช่วงวันที่และตัวกรอง ค้นด้วย VN/AN/HN/เลข REP/STM/INV ได้ตามหน้า
3. ดูยอดตาม HMAIN เพื่อระบุหน่วยบริการที่ต้องติดตาม
4. เปิดรายละเอียด visit และสถานะเพื่อดูเลขอ้างอิงผลตรวจ
5. ในส่วนตรวจ WALKIN อ่านสิทธิ์ที่ระบบใช้จริงและจำนวนรายการขาด
6. เปิดตรวจใบสั่งยา/หลักฐานก่อนเพิ่ม ไม่เพิ่มจากยอดรวมอย่างเดียว
7. หากได้รับอนุญาตให้เพิ่ม พิมพ์ข้อความยืนยัน **เพิ่ม WALKIN N รายการ** โดยใช้จำนวนจริงที่หน้าจอแสดง
8. หลังเพิ่มตรวจผลจำนวนสำเร็จ/ผิดพลาด และดึงรายการใหม่

หากมีการเปลี่ยนค่ารหัสสิทธิ์หรือ icode หลังรอบตรวจ ให้ตรวจใหม่ก่อนเพิ่ม ระบบปฏิเสธเมื่อการตั้งค่าต่างจากรอบตรวจ เพื่อลดการเพิ่มข้อมูลจากผลเก่า การมีรายการ WALKIN ไม่ใช่ผลอนุมัติชดเชย

## 18. มอนิเตอร์กองทุนพิเศษ Fee Schedule และโอกาสสร้างรายได้

### มอนิเตอร์กองทุนพิเศษ

กำหนดช่วงเวลา ดูภาพรวมกองทุน แล้วเจาะรายการที่มีคำเตือน แยกจำนวนครั้งบริการออกจากรายการที่ตรวจไม่ผ่าน ส่ง VN และเหตุผลให้ผู้รับผิดชอบกองทุนทบทวน หลังแก้ให้ดึงรอบเดิมเพื่อเทียบผล

### มอนิเตอร์ Fee Schedule

เปิด **มอนิเตอร์ Fee Schedule** กำหนดรอบ อ่านยอดและรายละเอียดรายการ FS ตรวจรหัสบริการ จำนวน และข้อมูลประกอบ หากยอดต่างจาก REP/STM ให้เทียบหลักฐานรายรายการก่อนปรับต้นทาง ยอดคำนวณตามกฎในระบบไม่แทนยอดอนุมัติจริง

### โอกาสสร้างรายได้

1. เปิด **การเงิน/ลูกหนี้ → โอกาสสร้างรายได้** กำหนดรอบวิเคราะห์
2. อ่านข้อสรุปและกลุ่มบริการที่ต้องพิสูจน์
3. เปิด worklist ค้น VN/AN และตรวจสาเหตุ/วิธีแก้ที่แสดง
4. แยกข้อมูลตกหล่นออกจากกรณีไม่ได้ให้บริการจริง
5. ให้ทีมที่รับผิดชอบยืนยันหลักฐานก่อนเติมข้อมูลหรือส่งเคลม
6. ติดตามจำนวนที่ตรวจแล้วและผลหลังแก้ ไม่ตั้งเป้าการแก้เพียงเพื่อเพิ่มยอด

ข้อเสนอหรือการแจ้งเตือนในหน้านี้เป็นจุดเริ่มต้นของการทบทวน ไม่ใช่คำสั่งเพิ่ม diagnosis/บริการ และไม่ใช่การรับรองรายได้ที่จะได้รับ

## 19. MOPH DMHT และ MOPH Vaccine

สองหน้านี้มีการตรวจสถานะและส่ง MOPH Claim จริง ต้องตั้งค่าการเชื่อมต่อและใช้บัญชีที่ได้รับมอบหมาย การทดสอบติดตั้งให้ตรวจข้อมูลก่อนและแยกจากการส่ง Production

### MOPH DMHT

1. เปิด **กองทุนเฉพาะ → MOPH DMHT** เลือกรอบบริการ
2. ดึงรายการ DM/HT Lab และค้น VN/HN/CID เมื่อจำเป็น
3. เปิดตรวจผล Lab รหัสรายการ และความครบถ้วนที่ระบบแสดง
4. เลือกรายการแล้วใช้ตรวจสอบสถานะก่อน เพื่อไม่ส่งซ้ำกับรายการที่มีสถานะแล้ว
5. แก้ข้อมูลที่ขาดตามหลักฐานและดึงใหม่
6. เลือกเฉพาะรายการพร้อม ส่ง MOPH Claim และตรวจผลรายรายการ
7. ส่งออก Excel เพื่อส่งต่องานได้ตามสิทธิ์และนโยบายข้อมูล

### MOPH Vaccine

1. เปิด **MOPH Vaccine** กำหนดรอบและสถานะส่งแล้ว/ยังไม่ส่ง
2. ตรวจรายการ EPI/dT และข้อมูลวัคซีนที่หน้าแสดง
3. ตรวจสถานะก่อนส่ง แยกรายการไม่พร้อมออกจากรายการที่เลือก
4. ส่งเฉพาะรายการที่ผ่านการทบทวน
5. ตรวจผลหลังส่งและเก็บรายการล้มเหลวไว้ติดตาม

หาก API timeout ให้ตรวจสถานะอีกครั้งก่อนส่งซ้ำ ไม่เปลี่ยนวัคซีนหรือผล Lab เพื่อให้ผ่านคำเตือนโดยไม่มีข้อมูลบริการจริง

## 20. ประกันสังคม: SSOP / AIPN และ REP/STM

### ส่งออก SSOP (ประกันสังคม)

1. เปิดเมนู **ประกันสังคม → ส่งออก SSOP (ประกันสังคม)**
2. เลือกโหมด OPD (SSOP) หรือ IPD (AIPN) ตามงาน หน้าแสดงชื่อโหมดปัจจุบัน
3. เลือกช่วงและเครือข่ายตามตัวกรอง แล้วดึงรายการ
4. ตรวจ VN สำหรับ OPD หรือ AN สำหรับ IPD รวมสิทธิ์ Dx รายการค่าใช้จ่าย และข้อผิดพลาด
5. เลือกรายการที่ผ่านการตรวจและสร้างชุดส่งออกตามโหมด
6. ตรวจไฟล์ที่ได้และดำเนินการนำส่งตามช่องทางประกันสังคมของโรงพยาบาล การสร้างไฟล์ไม่ได้ยืนยันว่าปลายทางรับแล้ว

### REP/STM ประกันสังคม

รองรับหน้ารับไฟล์ `.xlsx`, `.xls`, `.csv`, `.bil`, `.txt` แยกจากผล สปสช.

1. เลือกไฟล์ ตรวจประเภทและเครือข่ายในคิวนำเข้า
2. ดูตัวอย่างข้อมูลก่อนเริ่มนำเข้า
3. นำเข้าและตรวจประวัติ batch จำนวนแถว ยอดเคลม ยอดรับ และจำนวนติดปัญหา
4. เทียบกับไฟล์ส่งออกและเลขอ้างอิงของโหมดนั้น
5. หากอ่านรูปแบบไม่ได้ ให้เก็บไฟล์ต้นฉบับและส่งรายละเอียดรูปแบบให้ IT โดยปกปิดผู้ป่วย ไม่เปลี่ยนสกุลไฟล์อย่างเดียวเพื่อบังคับนำเข้า

## 21. บัญชีลูกหนี้สิทธิ

**เมนู:** การเงิน/ลูกหนี้ → บัญชีลูกหนี้สิทธิ • **ผลลัพธ์:** ชุดบัญชีที่ตรวจที่มาและรอบข้อมูลได้

1. กำหนดช่วงวันที่ ประเภทผู้ป่วย สิทธิ์ HOSxP และสิทธิการเงิน
2. ตรวจบัญชีที่เลือกและดึงข้อมูลรอบนั้น
3. กรอกลูกหนี้ยกมาต้นงวด หรือใช้ **ดึงยอดล่าสุด** แล้วตรวจว่าชุดก่อนหน้าตรงงวด/ขอบเขตเดียวกัน
4. ใส่หมายเหตุชุดลูกหนี้ที่บอกรอบและผู้รับผิดชอบ
5. ตรวจตารางราย visit แยกยอดเรียกเก็บ ชดเชย และผลต่างตามคอลัมน์ที่แสดง
6. ตรวจรายการที่จะตั้งลูกหนี้ก่อนบันทึกชุด ไม่ใช้การค้นหาในตารางแทนการตรวจขอบเขตทั้งหมด
7. บันทึกและตรวจประวัติชุดบัญชีล่าสุด รวมทั้งรายงานพิมพ์/ส่งออกตามปุ่มที่หน้าเปิดให้ใช้
8. ส่งให้ผู้ตรวจบัญชีทวนยอดและหลักฐาน แล้วเก็บเลขชุดสำหรับรอบถัดไป

### จุดตรวจยอดยกมา

ใช้ชุดงวดก่อนที่สรุปแล้วและขอบเขตสิทธิ์เดียวกัน หากเปลี่ยนยอดยกมาด้วยมือ ให้บันทึกเหตุผลและหลักฐาน ไม่รวมชุดซ้ำ การแก้ชุดบัญชีในแอปไม่แก้ราคาบริการใน HOSxP และไม่สร้างรายการรับเงินในระบบบัญชีอื่นโดยอัตโนมัติ

คู่มือเฉพาะลูกหนี้เดิมใน `docs/manual_accounts_receivable.html` ใช้เป็นเอกสารเสริม หากชื่อเมนูต่างให้ยึดฉบับนี้และหน้าจอปัจจุบัน

## 22. กระทบยอด สรุปรายวัน และ PPFS

### กระทบยอด REP/STM

1. ตรวจว่านำเข้าไฟล์ที่เกี่ยวข้องสำเร็จแล้ว
2. เปิด **กระทบยอด REP/STM** เลือกช่วงและตัวกรอง
3. ตรวจ visit ที่พบ REP แต่ยังไม่มี STM และ visit ที่มีผลต่าง
4. เปิดรายละเอียดเพื่อดูเลขอ้างอิงและรายการที่ใช้จับคู่
5. ถ้าจับคู่ไม่ได้ ตรวจ VN/AN/Tran ID วันที่และงวดก่อนแก้ข้อมูล
6. บันทึกประเด็นที่ต้องติดตาม แยกเหตุผล “ยังไม่ถึงงวด”, “ไฟล์ไม่ครบ”, “ข้อมูลอ้างอิงไม่ตรง” และ “ปฏิเสธจ่าย”

### สรุป REP รายวัน

เลือกวัน OPD/IPD/ทั้งหมด และตัวกรอง UUC1/UUC2 ตามหน้า เปิดรายละเอียด visit เพื่ออธิบายยอดรายวัน ตรวจความหมายตัวกรองจากข้อมูลจริง ไม่สรุปสถานะผู้ป่วยทั้งหมดจากชื่อ UUC อย่างเดียว

### เทียบยอดจัดสรร PPFS

กำหนด HCODE รอบ และตัวชี้วัด ค้นชื่อกลุ่มบริการ แล้วเทียบยอดที่หน้าจอแสดงกับข้อมูลจัดสรรของรอบเดียวกัน จำนวนบริการกับยอดจัดสรรอาจมีรอบเวลาคนละแบบ ต้องบันทึกช่วงที่ใช้เปรียบเทียบเสมอ

### จับคู่บริการ PPFS

เลือก OPD/IPD สิทธิ์ สถานะ และช่วงเวลา ค้นด้วย VN/HN/รายการ/Tran ID เปิดผลจับคู่รายบริการ ตรวจบริการซ้ำและรายการที่ยังจับคู่ไม่ได้ การจับคู่ได้เป็นความเชื่อมโยงข้อมูล ไม่ใช่หลักฐานการรับเงินจริง

## 23. ภาพรวมประกัน บัญชีประมาณการ และ Dashboard

### ภาพรวมประกันสุขภาพ

เปิดเมนู เลือกขอบเขตรายงานและรหัสบัญชี/สิทธิ์ตามหน้า ตรวจแหล่งข้อมูลและคอลัมน์ก่อนส่งออก ตั้งชื่อไฟล์ให้บอกรอบและประเภทข้อมูล ใช้ภาพรวมเพื่อหากลุ่มที่ต้องเจาะ ไม่ใช้แทนรายการบัญชีที่ผู้ตรวจลงนาม

### รายงานบัญชี / ประมาณการรายได้

1. เลือกปีงบประมาณและดึงข้อมูลประกอบ
2. ตรวจการจัดกลุ่มสิทธิ์ OPD/IPD และจำนวน Visit/SumAdjRW ที่ใช้คำนวณ
3. กรอกอัตราสมมติฐานตามที่ฝ่ายบัญชีอนุมัติ แยกจากอัตราจ่ายจริง
4. ตรวจผลคูณและยอดรวม: OP Visit × Charge Per Visit หรือ SumAdjRW × Charge Per RW ตามตาราง
5. ช่องว่างหรือค่าที่ไม่ใช่ตัวเลขถูกใช้เป็น 0 ตามหน้าปัจจุบัน จึงต้องตรวจว่าไม่ได้ลืมกรอกอัตราก่อนสรุป
6. ส่งออก/พิมพ์พร้อมบันทึกสมมติฐาน ปี และผู้ตรวจ

### Dashboard ภาพรวม

ตั้งช่วงวันที่ ตรวจจำนวนผ่าน/รอแก้และยอด จากนั้นกดเจาะรายการที่เกี่ยวข้อง เมื่อกลับจากหน้ารายการให้ตรวจตัวกรองอีกครั้งก่อนเทียบยอด Dashboard เป็นมุมมองติดตามงาน ไม่ใช่การปิดบัญชี

## 24. ศูนย์รายงานโรงพยาบาล AI และศูนย์ตรวจสอบ LINE

### ศูนย์รายงานโรงพยาบาล

1. เปิด **รายงาน/สถิติ → ศูนย์รายงานโรงพยาบาล** เลือกหมวดและรายงาน
2. อ่านป้ายความพร้อมของรายงานและข้อกำหนดแหล่งข้อมูล
3. กรอกช่วงวันที่หรือ HN/VN/AN ให้ตรงชนิดรายงาน
4. ระบุเงื่อนไขเพิ่มเติมเท่าที่จำเป็น แล้วสร้างรายงาน
5. อ่านผลและตรวจตัวอย่างกับต้นทางก่อนดาวน์โหลดไฟล์
6. เก็บไฟล์ตามสิทธิ์และลบสำเนาชั่วคราวตามนโยบายโรงพยาบาล

| สถานะ | รายงานตามหน้าโค้ดที่ตรวจ |
| --- | --- |
| พร้อมตามแหล่งที่รองรับ | สรุปประวัติการรักษา, รับ/ส่งต่อ, ภาพรวมรายวัน, ภาระงาน OPD, ทะเบียนรับ/จำหน่าย IPD, ผลงานวอร์ด, การใช้ยา, งาน Lab, ความครบก่อนเคลม, อันดับโรค OPD, สัดส่วนสิทธิ์, ค่าใช้จ่ายแยกหมวด, รายงานผู้รับบริการ/ราย visit แยก รพ.สต. |

| ต้องเชื่อมแหล่งข้อมูลเพิ่ม | ความหนาแน่น ER, อัตรากำลัง/ตารางเวร, คลังยา, Incident, HAI, ข้อร้องเรียน/ความพึงพอใจ |

### FDH AI Analytics และผู้ช่วย AI

เริ่มด้วยคำถามที่ระบุช่วงเวลา ขอบเขต หน่วยนับ และผลลัพธ์ เช่น “สรุปจำนวนครั้ง OPD แยกสิทธิ์วันที่ที่กำหนด เป็น Excel ไม่รวมข้อมูลระบุตัวบุคคล” หากต้องการรายบุคคลให้ยืนยันตัวระบุที่ถูกต้องและมีสิทธิ์เข้าถึง

1. ตรวจว่า AI พร้อมใช้งานและบัญชีมีสิทธิ์
2. พิมพ์คำขอให้ครบ หากระบบถามเพิ่มให้ตอบข้อมูลที่ขาด
3. ตรวจแหล่งข้อมูล ช่วงวันที่ เงื่อนไข และคำเตือนที่ตอบกลับ
4. เทียบยอดตัวอย่างกับรายงานมาตรฐานก่อนเผยแพร่
5. ดาวน์โหลดไฟล์เมื่อผลถูกต้อง หากสร้างไม่ได้ให้ลดช่วงหรือแบ่งคำถาม

AI สำหรับ query ถูกจำกัดให้อ่านข้อมูล ไม่ใช้สั่งแก้ SQL/เพิ่มบริการแทนหน้าทำงานที่ได้รับอนุญาต คำตอบ AI ต้องตรวจโดยผู้รับผิดชอบ และโมเดลภายนอกต้องอยู่ภายใต้นโยบายข้อมูลของโรงพยาบาล

### ศูนย์ตรวจสอบ (LINE)

ดู Action List และรายการที่ควรแก้ เลือกห้องสนทนาแล้วส่งข้อความให้ผู้รับผิดชอบ ระบุรอบ เมนู และเลขงานเท่าที่จำเป็น ในช่องข้อความ Enter ส่งข้อความ ส่วน Shift+Enter ขึ้นบรรทัดใหม่ หน้าแนบไฟล์/ภาพได้ตามชนิดที่กำหนด ให้ปกปิดข้อมูลก่อนแนบ

การตั้ง LINE Bot หรือรายงานตามเวลาเป็นงานผู้ดูแล ต้องยืนยันห้อง/กลุ่มปลายทางและผู้รับก่อนส่ง ข้อความในศูนย์ทีมกับผลส่งถึง LINE ภายนอกต้องตรวจสถานะจริงแยกกัน

## 25. สมาชิก การจัดการ batch คู่มือกองทุน และ ICD-9

### สมาชิกและสิทธิ์เมนู

1. เข้า admin เปิด **บริหารระบบ → สมาชิกและสิทธิ์เมนู**
2. สร้างกลุ่มตามหน้าที่ เลือกเมนูที่จำเป็น แล้วบันทึก
3. เพิ่มบัญชีรายคน ระบุชื่อแสดงและกลุ่ม ตรวจสถานะใช้งาน/admin
4. ทดสอบด้วยบัญชีผู้ใช้จริงที่กำหนดสิทธิ์ ไม่ใช้ admin ทดสอบการซ่อนเมนู
5. เมื่อย้ายหน้าที่ให้ปรับกลุ่ม เมื่อพ้นหน้าที่ให้ปิดบัญชี
6. ตรวจว่ามีผู้ดูแลที่ใช้งานได้ก่อนเปลี่ยนสิทธิ์บัญชีผู้ดูแล

### จัดการฐานข้อมูล REP/STM

หน้าปัจจุบันใช้ค้นหาและลบ **Batch REP/STM/INV** ไม่ใช่เครื่องมือแก้ SQL ทั่วไป

1. ค้น batch ด้วยเลขชุด ชื่อไฟล์ sheet ผู้นำเข้า หรือหมายเหตุ
2. เปิดดูรายละเอียดและยืนยันว่าเป็นชุดที่ผิดจริง
3. เก็บไฟล์ต้นฉบับและสำรองตามนโยบายก่อนลบ
4. ระบุเหตุผลและอ่านข้อความยืนยันลบ batch ให้ครบ
5. หลังลบตรวจประวัติ/ยอดที่เกี่ยวข้อง และนำเข้าไฟล์ที่ถูกต้องเมื่อจำเป็น

การลบ batch มีผลต่อผลติดตามและกระทบยอด ไม่ใช้เพียงเพื่อทำให้คำเตือนหาย

### คู่มือกองทุนและค้นหารหัสหัตถการ ICD-9

ใช้ **คู่มือกองทุน** ดูคำอธิบาย ช่องทาง และรหัสที่โปรแกรมรู้จัก โดยเทียบประกาศที่หน่วยงานใช้จริง หากมีข้อมูลขัดกันให้ส่งให้ผู้ดูแลกฎตรวจสอบ

ใช้ **ค้นหารหัสหัตถการ ICD-9** ค้นรหัส/คำอธิบาย แล้วตรวจความหมายกับหัตถการที่บันทึกจริง การค้นพบรหัสไม่ใช่การยืนยันว่า visit นั้นทำหัตถการดังกล่าว และไม่ควรเพิ่ม code โดยไม่มีหลักฐาน

## 26. อัปเดตระบบจาก GitHub และย้อนเวอร์ชัน

### ก่อนอัปเดต

ตรวจ branch/commit, working tree สะอาด, dependency, พื้นที่ว่าง, backup และ PM2 ของบัญชีบริการ ปุ่มอัปเดตใช้ branch ที่ตั้งในเซิร์ฟเวอร์ ไม่ได้รวมทุก branch ใน GitHub ให้เป็นรุ่นเดียวกัน

```bash
cd /opt/FDHChecker
git branch --show-current
git rev-parse HEAD
git status --short
pm2 describe fdh-backend
pm2 describe fdh-frontend
curl --fail --max-time 10 http://127.0.0.1:3506/api/ready
```

### ผ่านหน้าเว็บ

1. เข้า admin เปิด **ตั้งค่าระบบ → อัปเดตระบบ**
2. ตรวจรุ่นใหม่ อ่าน branch commit และรายละเอียดสิ่งที่จะเปลี่ยน
3. ตรวจว่ามีงานเดิมค้างหรือไม่ หากมีให้ตรวจ log ก่อนเริ่มซ้อน
4. ยืนยันอัปเดต รอขั้นเชื่อมต่อ ดาวน์โหลด dependency ทดสอบ build รีสตาร์ต และ health check
5. ระหว่างรีสตาร์ตหน้าเว็บอาจขาดการเชื่อมต่อชั่วคราว รอการติดตามงานเดิม
6. ถือว่าสำเร็จเมื่อสถานะงานระบุสำเร็จ รุ่นที่รันถูกต้อง และทดสอบ API/หน้าเว็บผ่าน ไม่ดูแถบ 100% อย่างเดียว

### ครั้งแรกที่ runner รุ่นเก่ามีปัญหา

รุ่นเก่าอาจคัดลอก runner ก่อน pull จึงยังใช้ logic เก่าในการอัปเดตรอบนั้น หลังยืนยันว่างานเดิมจบแล้ว ใช้ SSH ด้วยบัญชีบริการและรันทีละคำสั่ง หยุดทันทีเมื่อผิดพลาด:

```bash
cd /opt/FDHChecker
git pull --ff-only
npm ci --include=dev
npm run check
npm run build:all
pm2 restart fdh-backend
pm2 restart fdh-frontend
curl --fail --max-time 10 http://127.0.0.1:3506/api/live
curl --fail --max-time 10 http://127.0.0.1:3506/api/ready
```

ชุดนี้เปลี่ยนโปรแกรมและรีสตาร์ตบริการ ต้องใช้ในช่วงที่ผู้รับผิดชอบอนุมัติ ตรวจ upstream ก่อน `pull` และใช้ชื่อ PM2 จริงหากไซต์ตั้งต่างจากตัวอย่าง

### สถานะค้างและหลักฐาน

```bash
cd /opt/FDHChecker
cat .update-state/current.json
ls -lt .update-state/update-*.log
pm2 status
pm2 logs fdh-backend --lines 80 --nostream
```

ไฟล์สถานะอยู่ใน project ไม่ใช่ home ของ SSH user ขั้น testing ล้มมักต้องอ่าน error ตัวแรกและบทสรุป test; ขั้น 89% เกี่ยวกับ restart; 95% เป็น health check แถบ 100% อาจเป็นงานล้มที่สิ้นสุดแล้ว ให้ดู `status` และข้อความ

### ย้อนเวอร์ชัน

เลือก commit ก่อนหน้าที่รู้ว่าใช้งานได้ในส่วนย้อนเวอร์ชัน อ่านรายละเอียดและยืนยันในช่วงเวลาที่กำหนด การย้อนโปรแกรมไม่ย้อนข้อมูลฐาน จึงต้องตรวจความเข้ากันได้ของ schema หากต้องกู้ผ่าน SSH ให้เก็บ commit/ไฟล์ตั้งค่าปัจจุบันและทำตามแผนของ IT ไม่ใช้ `git reset --hard` กับ checkout ที่มีงานแก้ค้างโดยไม่ตรวจ

## 27. สำรองข้อมูล กู้คืน และบำรุงรักษา

### สิ่งที่ต้องสำรอง

| ชุดข้อมูล | เหตุผล |
| --- | --- |
| ฐาน REPSTM/แอป | ผู้ใช้ การตั้งค่า ผลนำเข้า และประวัติงาน |
| `.env` และ `.secrets` | การเชื่อมต่อและค่ารายไซต์ ต้องเข้ารหัส/จำกัดสิทธิ์ |
| ไฟล์ต้นฉบับ REP/STM/INV และเอกสารแนบที่ใช้งานจริง | ใช้ตรวจย้อนหลังและนำกลับเข้าเมื่อจำเป็น |
| commit/branch และ config PM2/Nginx/systemd | ใช้ประกอบคืนบริการให้ตรงรุ่น |
| HOSxP | อยู่ในแผนสำรองของโรงพยาบาลแยกต่างหาก |

### ใช้สคริปต์สำรองที่มีใน repository

```bash
cd /opt/FDHChecker
FDH_PROJECT_DIR=/opt/FDHChecker bash deploy/scripts/backup-databases.sh
```

สคริปต์ Bash อ่าน `.env` แล้วใช้ `mysqldump` สำรอง REPSTM เป็น `.sql.gz` ตรวจด้วย `gzip -t` และไม่ลบของเก่าอัตโนมัติ ต้องใช้ไฟล์ `.env` ที่เชื่อถือได้และมีรูปแบบ shell-compatible

**ข้อจำกัดที่พบจากโค้ด:** สคริปต์ Bash รุ่นที่ตรวจไม่ได้ส่งตัวเลือก `--port` ให้ `mysqldump` จึงไม่ควรใช้เป็นขั้นตอนสำรองฐานพอร์ตพิเศษโดยไม่ปรับและทดสอบก่อน ไม่ใช้สคริปต์ MySQL นี้สำรอง PostgreSQL และไม่เปิด `FDH_BACKUP_HOSXP=1` โดยไม่มีแผนรองรับฐานโรงพยาบาลขนาดใหญ่

### ทดสอบกู้คืน

1. ตรวจชื่อไฟล์ ขนาด วันเวลา และความสมบูรณ์ของ archive
2. ให้ DBA เตรียมฐานทดสอบชื่อใหม่ ห้าม restore ทับ Production เพื่อทดลอง
3. restore ตามชนิดฐานและเครื่องมือที่โรงพยาบาลอนุมัติ
4. ชี้ระบบทดสอบไปฐานกู้คืน ตรวจผู้ใช้ การตั้งค่า จำนวน batch และรายงานตัวอย่าง
5. ตรวจไฟล์แนบและค่าหน่วยบริการที่ไม่ได้อยู่ใน SQL dump
6. บันทึกเวลาที่ใช้ ข้อมูลที่สูญได้ และผลตรวจเทียบ
7. เมื่อเกิดเหตุจริงให้เลือกจุดกู้คืนร่วมกับเจ้าของข้อมูลก่อนดำเนินการ

### รอบบำรุงรักษา

รายวัน: API/ฐานพร้อม พื้นที่ว่าง งานค้าง และ backup สำเร็จ • รายสัปดาห์: ข้อผิดพลาดซ้ำ ไฟล์ค้าง/ซ้ำและบัญชีที่ผิดปกติ • รายเดือน: ทดสอบ restore ตรวจสิทธิ์และรอบไฟล์ • ก่อนอัปเดตใหญ่: backup รุ่นเดิม แผนย้อน และผู้ตรวจรับแต่ละงาน

### DNS บน AlmaLinux

เริ่มด้วย `timeout 5 getent ahostsv4 github.com` และ curl แบบจำกัดเวลา หากขึ้น resolving timed out ให้ตรวจ NetworkManager และเส้นทางออกไป DNS จริง การใส่ `1.1.1.1` ใน `ipv4.dns-search` ไม่ได้เพิ่ม DNS server; dns-search เป็น suffix ของชื่อโดเมน ไม่ควรใส่ IP ที่ช่องนั้น ใช้ DNS ที่ผู้ดูแลเครือข่ายยืนยันและตรวจทั้ง UDP/TCP 53 กับ HTTPS 443 ตามนโยบาย

### ข้อมูลสำหรับส่ง ticket

ส่งเวลาเกิดเหตุ ชื่อเมนู commit/branch ผู้ใช้ตามหน้าที่ ตัวกรอง ขั้นตอนทำซ้ำ ข้อความผิดพลาด และ request ID ถ้ามี แนบ log เฉพาะช่วงที่เกี่ยวข้องพร้อมปกปิดรหัสผ่าน token ชื่อ/เลขบัตรผู้ป่วย ไม่ส่ง `.env` ทั้งไฟล์

## 29. ตรวจรับและอบรมก่อนใช้งานจริง

ใช้ระบบทดสอบหรือรอบที่ได้รับอนุมัติ ตรวจแบบอ่านก่อน ปุ่มส่งเคลม เพิ่ม WALKIN ปิดสิทธิ ลบ batch และส่ง LINE ให้แยกทดสอบตามสิทธิ์และแผนที่กำหนด

| งานตรวจรับ | วิธีพิสูจน์ | ผู้ตรวจ |
| --- | --- | --- |
| ติดตั้ง | reboot แล้วบริการกลับมา; live/ready/หน้าเว็บผ่าน | IT |
| หน่วยบริการ | ชื่อ HCODE สิทธิ์ WALKIN และหมู่บ้านตรงไซต์ | IT + ประกัน |
| บัญชี | admin และผู้ใช้ทั่วไปเห็นสิทธิ์ตามกลุ่ม | ผู้ดูแล |
| OPD | ตัวอย่างมี Dx ยา Lab หัตถการตรง HIS | เวชระเบียน |
| IPD | AN วันรับ/จำหน่าย Dx/Procedure/ยาและ audit ตรวจได้ | เวชระเบียน IPD |
| ส่งออก | จำนวนที่เลือกและไฟล์ตรงรอบ; แยกการส่งจริง | งานเคลม |
| กองทุน | อย่างน้อยหนึ่งเคสผ่าน หนึ่งเคสเตือน และหนึ่งเคสประวัติไม่ครบ | เจ้าหน้าที่กองทุน |
| ANC | ครรภ์เดียวหลาย visit ตรวจซ้ำได้; ครรภ์ไม่ทราบถูกแจ้งทบทวน | งาน ANC |
| ผลตอบกลับ | ไฟล์ทดสอบนำเข้าสำเร็จ จับคู่และตรวจ C ได้ | ประกัน |
| ลูกหนี้ | ยกมาและยอดงวดเทียบหลักฐานได้ | การเงิน |
| รายงาน | จำนวนคน/ครั้งและขอบเขตพื้นที่ตรงนิยาม | เจ้าของรายงาน |
| อัปเดต | staging ใช้ topology จริง อัปเดตและย้อนรุ่นที่อนุญาตได้ | IT |
| Backup | restore ฐานทดสอบและตรวจข้อมูลสำคัญผ่าน | DBA + เจ้าของข้อมูล |

### แบบฝึกอบรม

ให้ผู้เรียนใช้ข้อมูลจำลอง `VN-DEMO-001`: ค้น OPD → เปิดรายละเอียด → ระบุปัญหา → ตั้งผู้รับผิดชอบในคิว → ตรวจซ้ำ → เตรียมส่งออก → อ่านผลตอบกลับจำลอง → อธิบายยอดให้การเงิน จากนั้นทำ IPD ด้วย `AN-DEMO-001` ผู้สอนตรวจความเข้าใจเรื่องพร้อมส่ง/ส่งแล้ว/ได้รับชดเชยก่อนให้ใช้ Production

### บันทึกส่งมอบ

เก็บวันติดตั้ง branch/commit URL ผู้รับผิดชอบแต่ละงาน วิธีเข้าเครื่อง ตำแหน่งสำรอง รอบสำรอง ผลทดสอบ และข้อจำกัดค้างไว้ในพื้นที่ภายใน แยกความลับออกจากเอกสารแจกอบรม

## 30. มือถือ แหล่งอ้างอิงโค้ด และขอบเขตเอกสาร

### มือถือ

เว็บใช้งานตาม URL ของโรงพยาบาล ส่วนแอป Capacitor มี URL ใน config ของ native app ไม่เปลี่ยนตาม IP เซิร์ฟเวอร์ใหม่เอง ก่อนแจกโรงพยาบาลอื่นให้ตรวจ `capacitor.config.*`, CORS, HTTPS และข้อยกเว้นเครือข่ายของ Android/iOS หากเปลี่ยน URL native ต้อง sync/build และติดตั้งแอปรุ่นใหม่ตาม `docs/MOBILE_CONNECTION.md`

### หลักฐานที่ใช้จัดทำ

เมนูและสิทธิ์: `src/config/menuDefinitions.ts`, `src/App.tsx` • ขั้นตอนหน้าจอ: `src/pages/` และส่วนตั้งค่าใน `src/components/` • กองทุน: `src/config/fundDefinitions.ts`, `fundRuleCatalog.ts` และ `docs/HOSPITAL_SETUP.md` • ตัวแปรฐาน: `server/hospitalDatabaseConfig.ts` • CORS: `server/index.ts` • bootstrap: `server/repositories/system.repository.ts` • ติดตั้ง/backup/updater: `deploy/`, `package.json`

คู่มือนี้ตรวจความสอดคล้องกับโค้ด ไม่ได้ส่งเคลม ทดลองเขียนข้อมูลผู้ป่วย หรือยืนยันการเชื่อมทุกฐานโรงพยาบาลจริงระหว่างจัดทำ รายการทดสอบรับระบบในบท 29 ต้องทำเพิ่มที่แต่ละไซต์ ความพร้อมของรายงานเป็นสถานะที่โปรแกรมประกาศและขึ้นกับข้อมูลที่เชื่อมได้
