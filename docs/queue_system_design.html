02 · Pain Points

สิ่งที่ทำให้คิวช้า เปราะบาง และตรวจสอบย้อนหลังไม่ได้

💥

สถานะหายเมื่อ restart

สถานะงาน, log 100 บรรทัด และ flag isExecuting อยู่ในหน่วยความจำ ถ้า PM2 restart (เช่น หน่วยความจำเกิน 1G) งานที่ทำค้างจะหายโดยไม่มีประวัติ

🐢

ทำงานต่อกันเป็นเส้นเดียว

Sync worker ดาวน์โหลด แปลง xlsx และ INSERT ในลูปเดียวกัน browser ต้องรอ DB ทุกไฟล์ และมี waitForTimeout แบบรอตายตัวหลายจุด

🔁

ไม่มีการลองใหม่ หรือ Dead-letter

ไฟล์ที่ดาวน์โหลดไม่สำเร็จจะเพิ่มแค่ errorCount ไม่มี backoff ไม่มีการลองซ้ำ และไม่มีที่ให้กดลองใหม่

🗝️

คีย์ Work Queue ไม่ครอบคลุม IPD

มี UNIQUE KEY uk_vn (vn) อย่างเดียว ไม่แยก OPD/IPD (AN) และไม่แยก hcode assigned_to เป็นข้อความอิสระ และไม่มีประวัติการเปลี่ยนสถานะ

🧮

ตัวเลขสรุปไม่ตรงจริง

หน้า WorkQueuePage นับสถานะจากรายการที่โหลดมาไม่เกิน 500 แถว ถ้างานค้างมากกว่านั้น ตัวเลขสรุปจะต่ำกว่าจริง

🐌

คำสั่ง SQL ที่สิ้นเปลือง

รัน CREATE TABLE IF NOT EXISTS ทุก request, bulk insert ทีละแถว (สูงสุด 2,000 round-trip), ค้นหาแบบ LIKE '%…%' ที่ต้องสแกนทั้งตาราง และมี DDL ซ้ำ 2 ไฟล์

อ้างอิง: claims.repository.ts#L1920-2054, collaboration.ts#L59, schema.ts#L385, eclaimBackgroundWorker.ts, deploy/pm2/ecosystem.config.cjs

03 · Design Principles

หลักการ 6 ข้อของ Unified Queue

💾

Durable

ทุกงานต้องบันทึกใน MySQL ก่อนลงมือทำ ถ้า restart งานจะไม่หาย และรู้ว่าหยุดอยู่ขั้นไหน

🧷

Idempotent

ทุกงานมี dedupe_key เช่น SHA-256 ของไฟล์ REP กดซ้ำหรือลองใหม่ก็ไม่ทำให้ข้อมูลซ้ำ

🛣️

Lane isolation

แยกช่องทำงานตามทรัพยากร เช่น browser, hosxp-db, external-api งานหนักในช่องหนึ่งจะไม่ไปบล็อกช่องอื่น

🔭

Observable

มีความยาวคิว อายุงานที่เก่าที่สุด อัตราล้มเหลว และ p95 duration แสดงบน dashboard และแจ้งเตือนได้

🛡️

Secure by default

payload เก็บแค่ reference (VN/batch id/path) ไม่เก็บชื่อหรือ CID ผู้ใช้ที่สั่งงานมาจาก session และงานภายนอกต้องผ่านสิทธิ์ระดับ action

🧱

No new infra first

ใช้ MySQL + Node process เดิม (PM2 fork) ถ้าในอนาคตต้องขยาย ค่อยเปลี่ยนเป็น Redis/BullMQ ผ่าน interface เดียวกัน

05 · Job Queue Schema

ตาราง job_queue: คิวที่ไม่หาย และไม่ถูกหยิบซ้ำ

CREATE TABLE job_queue (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  hcode         VARCHAR(10)  NOT NULL,
  job_type      VARCHAR(64)  NOT NULL, -- eclaim.sync.rep, repstm.import.file …
  lane          VARCHAR(32)  NOT NULL, -- browser | import | hosxp-db | external-api
  status        ENUM('queued','running','succeeded',
                     'failed','dead','cancelled') NOT NULL,
  priority      TINYINT NOT NULL DEFAULT 5,
  run_at        DATETIME(3) NOT NULL,
  attempts      SMALLINT DEFAULT 0, max_attempts SMALLINT DEFAULT 5,
  dedupe_key    VARCHAR(191) NULL,     -- sha256 ไฟล์ / type+range
  parent_id     BIGINT NULL,
  payload_json  JSON NOT NULL,        -- reference only, ห้ามมี PII
  progress_json JSON NULL, last_error VARCHAR(1000),
  claim_token   CHAR(36) NULL, locked_by VARCHAR(64),
  lease_until   DATETIME(3) NULL,
  created_by    INT NULL,              -- user id จาก session
  created_at, started_at, finished_at DATETIME(3),
  UNIQUE KEY uk_dedupe (job_type, dedupe_key),
  KEY ix_pick (status, lane, run_at, priority),
  KEY ix_parent (parent_id)
);

🎯 การ Claim แบบ portable (MySQL 5.7+/MariaDB)

UPDATE job_queue
   SET status='running', claim_token=?, locked_by=?,
       lease_until=NOW(3)+INTERVAL ? SECOND,
       attempts=attempts+1, started_at=NOW(3)
 WHERE status='queued' AND lane=? AND run_at<=NOW(3)
 ORDER BY priority DESC, id
 LIMIT 1;
SELECT * FROM job_queue WHERE claim_token=?;

UPDATE แถวเดียวเป็น atomic อยู่แล้ว จึงไม่มีทางที่ 2 worker หยิบงานเดียวกันได้ ถ้าใช้ MySQL 8 สามารถเปลี่ยนเป็น FOR UPDATE SKIP LOCKED เพื่อรับปริมาณงานได้มากขึ้น

♻️ Reaper ทุก 30 วินาที

งานที่ status='running' แต่ lease_until < NOW() (process ตายหรือค้าง) จะถูกคืนเป็น queued พร้อม backoff ถ้าลองครบ max_attempts แล้วจะย้ายเป็น dead

06 · Lifecycle · Retry · DLQ

วงจรชีวิตงาน และนโยบายลองใหม่

queued→ running→ succeeded
running ✕ error → failed (retryable)→ backoff → queued · ครบ max_attempts → dead (DLQ) · ผู้ใช้กดหยุด → cancelled

⏱️ Exponential backoff + jitter

delay = min(cap, base × 2^attempt)
      × random(0.5 … 1.0)
base = 30s · cap = 30m

ป้องกันการยิงซ้ำพร้อมกันทั้งชุดตอนเว็บ สปสช. หรือ FDH ล่ม

🧭 แยกประเภท error

  • retryable timeout, 5xx, เบราว์เซอร์ค้าง, DB deadlock
  • fatal ไฟล์เสีย, hcode ไม่ตรง, schema ผิด → ย้ายเป็น dead ทันที
  • auth FDH 401 “Token หมดอายุ” หรือ e-Claim session หมด → หยุดทั้ง lane แล้วแจ้งให้ login

🪦 Dead-letter = งานที่ต้องมีคนดู

หน้า Admin แสดงงาน dead พร้อม last_error และปุ่ม Retry / Cancel ทุกการกดบันทึกลง audit event และสรุปส่ง LINE วันละ 1 ครั้ง (ไม่มี PII)

ข้อความ 401 “Token หมดอายุ” อ้างอิง MOPH FDH Manual V3 หัวข้อ 3.3.1 ใน Vault (knowlage/vault/MOPH_FDH_MANUAL_V3.md)

08 · Scheduler

เปลี่ยน setInterval 3 ตัว เป็น Scheduler ตัวเดียวที่เก็บค่าใน DB

ก่อน: แต่ละ service ทำ scheduler ของตัวเอง

// ucWalkinAutoBatchService.ts
schedulerTimer = setInterval(() => {
  void runUcWalkinBatchJob('scheduler') …
}, intervalMs);          // isExecuting อยู่ใน RAM

// nhsoAutoCloseService.ts
schedulerTimer = setInterval(async () => {
  if (isExecuting) return; …
}, intervalMs);          // ทุก 3 นาที
  • ถ้าเปิด 2 instance งานจะรันซ้ำ เพราะ lock อยู่ใน RAM
  • ไม่มีประวัติว่ารอบไหนพลาด หรือใช้เวลาเท่าไร
  • รอบที่พลาดตอน restart จะไม่ถูกรันชดเชย

หลัง: job_schedule + leader lock

CREATE TABLE job_schedule (
  name VARCHAR(64) PRIMARY KEY,
  job_type VARCHAR(64), cron_expr VARCHAR(64),
  enabled BOOLEAN, next_run_at DATETIME(3),
  last_job_id BIGINT, payload_json JSON
);
-- tick ทุก 15 วินาที (เฉพาะ leader)
SELECT GET_LOCK('fdh_scheduler_leader', 0);
-- เลือก schedule ที่ next_run_at <= NOW() แล้วใส่เป็นงานใน job_queue
-- dedupe_key = name:slot  →  ไม่สร้างงานซ้ำในรอบเดียวกัน
  • ค่าการตั้งเวลาเดิม (app_setting) ย้ายมาเก็บใน job_schedule และยังแก้จากหน้าเดิมได้
  • systemd timer fdh-duplicate-appointment ย้ายเข้ามาภายหลังได้ (ไม่บังคับ)

10 · Human Work Queue

Work Queue v2: state machine ที่มีเงื่อนไขกำกับ และมีประวัติทุกการเปลี่ยนสถานะ

new / triage→ รอแก้เวชระเบียน รอ Authen Code รอ ICD/ICD9 รอการเงิน→ พร้อมส่ง→ ส่งแล้ว→ ตีกลับ ↺ / ปิดงาน

ยังใช้ 7 สถานะเดิมจาก WorkQueuePage.tsx ทุกตัว เพิ่มแค่ new/triage และ ปิดงาน จึงใช้กับข้อมูลเดิมได้

🔑 คีย์และโครงสร้างใหม่

UNIQUE (hcode, visit_type, visit_ref)

  • จะเปลี่ยนเป็น ส่งแล้ว ต้องมีเลขอ้างอิงการส่ง หรือผลตอบกลับ (ตามคู่มือระบบข้อ 11)

  • ส่ง PUT พร้อม version ถ้าคนอื่นแก้ไปก่อนจะได้ 409 ป้องกันการเขียนทับกัน

12 · Priority · SLA · Aging

จัดลำดับงานด้วยคะแนน ให้ทีมเห็นงานที่ควรทำก่อน

สูตรคะแนนความสำคัญ (ปรับน้ำหนักได้)

score = w₁·Age + w₂·Amount + w₃·Due + w₄·Type

  • Age: จำนวนวันตั้งแต่ service_date (normalize เป็น 0–1)
  • Amount: ยอดเรียกเก็บของรายการ (normalize ตาม percentile ของรอบ)
  • Due: ความใกล้ถึงกำหนดส่งที่โรงพยาบาลตั้งไว้ต่อกองทุน
  • Type: น้ำหนักตามประเภท Deny / Corrective / Verify
กำหนดส่งและน้ำหนักต้องให้โรงพยาบาลเป็นผู้กำหนด ระบบไม่สร้างกติกาการจ่ายหรือเส้นตายของกองทุนขึ้นมาเอง เก็บเป็นค่าตั้งค่าที่มีแหล่งอ้างอิง

13 · Quick Wins · ทำได้ทันที

ปรับประสิทธิภาพ Work Queue ได้ทันที โดยยังไม่ต้องเปลี่ยนสถาปัตยกรรม

1 · Bulk insert แบบหลายแถว

// ก่อน: วนลูป INSERT ทีละแถว (สูงสุด 2,000 ครั้ง)
for (const item of items) await connection.query(`INSERT …`)

// หลัง: แบ่งก้อนละ 500 แถว ทำใน transaction เดียว
await conn.beginTransaction();
for (const chunk of chunks(items, 500))
  await conn.query(`INSERT INTO claim_work_queue (…) VALUES ?
    ON DUPLICATE KEY UPDATE …`, [chunk.map(toRow)]);
await conn.commit();

round-trip ลดจาก N เหลือ ⌈N/500⌉ ครั้ง และถ้าล้มกลางทาง ข้อมูลจะไม่ค้างครึ่งๆ กลางๆ

2 · เลิกสั่ง DDL ทุก request

// ก่อน: ทุก GET/PUT/bulk
await connection.query(CLAIM_WORK_QUEUE_TABLE_SQL);
// หลัง: ใช้ versioned migration ครั้งเดียว (ตาม BACKLOG P1)
//       หรืออย่างน้อย memoize ด้วย ensureOnce()

3 · Endpoint นับสถานะที่ฝั่งเซิร์ฟเวอร์

SELECT queue_status, COUNT(*) FROM claim_work_queue
 WHERE service_date BETWEEN ? AND ? GROUP BY queue_status;

4 · Index และ pagination

  • composite (queue_status, service_date, id) + keyset pagination แทน LIMIT 500
  • ค้น VN/HN แบบ prefix (LIKE 'x%') ส่วนการค้นชื่อแยกเป็นตัวเลือกเพิ่ม
  • ลบ DDL ที่ซ้ำกันใน collaboration.ts ให้เหลือที่เดียว
14 · Observability · Security

วัดผลได้ ตรวจสอบได้ และไม่ทำให้ข้อมูลผู้ป่วยรั่ว

📈 Metrics หลัก (endpoint /api/queue/metrics)

queue_depth{lane,status}จำนวนงานในคิวแยกตาม lane และสถานะ
oldest_queued_age_secondsอายุงานที่รอนานที่สุด ใช้ตรวจว่าคิวติดหรือไม่
job_duration_p95{type}ใช้ตั้ง timeout และ lease ตามข้อมูลจริง
job_failure_rate{type}อัตราล้มเหลวของแต่ละประเภทงาน
dead_jobs_totalถ้ามากกว่า 0 ให้แจ้งผู้ดูแล
work_items_sla_breachจำนวน work item ที่เกิน SLA แยกตามทีม

หน้าจอแสดง progress ผ่าน SSE (/api/jobs/:id/stream) แทนการ poll worker-status ซ้ำๆ

🛡️ กติกาความปลอดภัย

  • payload_json เก็บแค่ reference เช่น batch id, path หรือช่วงวันที่ ห้ามมี ชื่อ, CID หรือ HN
  • last_error และ log ต้องผ่าน redaction ก่อนบันทึก (สอดคล้อง P1 Structured logging)
  • created_by / actor มาจาก authenticated session เท่านั้น ไม่รับค่าจาก body
  • สิทธิ์ระดับ action: job:viewjob:retryjob:canceljob:external
  • ไฟล์ export (fdh.export.package) มี TTL ดาวน์โหลดได้เฉพาะเจ้าของงานหรือ admin
  • Retention: ลบงาน succeeded หลัง 30 วัน และ event หลัง 90 วัน (ค่าเริ่มต้นที่เสนอ ต้องยืนยันกับนโยบายโรงพยาบาล)
  • ขอบเขต AI read-only และ SQL validation ไม่เปลี่ยน AI อ่านสถานะคิวได้ แต่สั่งงานไม่ได้
15 · Roadmap

แผนปรับใช้ 5 เฟส: ทุกเฟส deploy แยกได้ และ rollback ได้

PHASE 0 · ~1 สัปดาห์

Quick wins

  • bulk insert แบบหลายแถว
  • ลบ DDL ที่รันทุก request
  • endpoint นับสถานะ
  • composite index + keyset pagination
PHASE 1 · ~2 สัปดาห์

Job core

  • migration job_queue/event/schedule
  • Runner + lanes + reaper
  • ย้าย UC Walk-in และ Auto Close
  • หน้า Admin Jobs / DLQ
PHASE 2 · ~2–3 สัปดาห์

e-Claim & Import

  • แยก scan / download / import
  • ย้าย REP Import จาก browser ไปเซิร์ฟเวอร์
  • FDH export เป็นงานเบื้องหลัง
  • SSE progress
PHASE 3 · ~3 สัปดาห์

Work Queue v2

  • คีย์ hcode+type+ref
  • state guard + version
  • routing จาก REP catalog
  • priority + SLA dashboard
PHASE 4 · เมื่อจำเป็น

Scale-out

  • แยก worker process ใน PM2
  • MySQL 8 SKIP LOCKED
  • ทางเลือก Redis/BullMQ ผ่าน interface เดิม

✅ Definition of Done ต่อเฟส

มี unit test (claim/lease/backoff/dedupe/guard), ผ่าน npm run check, มี migration + rollback note และอัปเดต README/BACKLOG ตาม BACKLOG “Definition of done”

🔀 ย้ายระบบแบบเปิด/ปิดได้

ใช้ feature flag ต่องาน (QUEUE_ENGINE=legacy|jobs) รันคู่กับของเดิม 1 รอบ เปรียบเทียบผล แล้วค่อยปิดของเดิม

⏳ ระยะเวลาโดยประมาณ

ประเมินสำหรับนักพัฒนา 1 คนที่รู้จักโค้ดชุดนี้ ต้องปรับตามผลการวัดจริงหลัง Phase 0
