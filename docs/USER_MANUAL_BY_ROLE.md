# คู่มือใช้งาน FDH Checker แยกตามหน้าที่

คู่มือนี้ใช้สำหรับแบ่งงานและสิทธิ์ของผู้ใช้งาน FDH Checker ตามหน้าที่จริงของโรงพยาบาล ชื่อบทบาทเป็นแนวทางสำหรับจัดกลุ่มผู้ใช้ในระบบ ผู้ดูแลระบบต้องกำหนดสิทธิ์เมนูให้แต่ละกลุ่มใน **บริหารระบบ → สมาชิก/กลุ่มผู้ใช้** อีกครั้งตามโครงสร้างของโรงพยาบาล

## 1. ภาพรวมการทำงาน

ลำดับงานมาตรฐานคือ

1. ตรวจสอบการเชื่อมต่อ HOSxP และช่วงวันที่
2. ตรวจสอบรายการ OPD/IPD และแก้ข้อมูลต้นทางใน HOSxP
3. ตรวจสอบกองทุนเฉพาะและรายการที่ระบบเตือน
4. ตรวจสอบก่อนส่ง FDH/e-Claim แล้วส่งข้อมูล
5. นำเข้าและจับคู่ REP / STM / INV
6. ติดตามรายการตีกลับ, C/Deny, ยอดลูกหนี้ และรายงานสรุป

หลักสำคัญคือแก้ข้อมูลที่ HOSxP แล้วดึงข้อมูลมาตรวจซ้ำ ไม่แก้ข้อมูลเคลมด้วยการเดาข้อมูลทางคลินิก และไม่ใช้ปุ่มเติมข้อมูลอัตโนมัติโดยไม่มีหลักฐานการให้บริการจริง

## 2. บทบาทและสิทธิ์ที่แนะนำ

| บทบาท | หน้าที่หลัก | เมนูที่ควรมี |
|---|---|---|
| ผู้ดูแลระบบ | ผู้ใช้ กลุ่ม สิทธิ์ การตั้งค่าระบบ และการกู้คืน | บริหารระบบ, ตั้งค่า, สมาชิก, คู่มือ |
| ผู้ดูแล HOSxP/IT | ฐานข้อมูล การเชื่อมต่อ รหัสมาตรฐาน และเซิร์ฟเวอร์ | ตั้งค่า, คู่มือ, รายงานระบบ, สถานะนำเข้า |
| เวชระเบียน/OPD | ตรวจรายการผู้ป่วยนอกและกองทุน | รายการ OPD, ส่งออก OPD, กองทุนเฉพาะ, ตรวจสอบก่อนส่ง |
| เวชระเบียน/IPD | ตรวจผู้ป่วยในและส่งออกข้อมูล | รายการ IPD, ส่งออก IPD, Monitor IPD Claim, ตรวจสอบก่อนส่ง |
| งานประกัน/เคลม | ส่งเคลม ติดตามผล และนำเข้าผลตอบกลับ | FDH/e-Claim, นำเข้า/ตรวจสอบ, REP/STM, รายการตีกลับ, ปิดสิทธิ์ |
| การเงิน/ลูกหนี้ | กระทบยอดรายรับ ลูกหนี้ และโอกาสรายได้ | การเงิน/บัญชี, ลูกหนี้, UUC1, นอก CUP, รายงาน REP |
| หัวหน้างาน/ผู้บริหาร | ดูภาพรวมและอนุมัติการติดตามงาน | Dashboard, รายงานโรงพยาบาล, ภาพรวมสิทธิ์, วิเคราะห์กองทุน |
| ผู้ใช้ AI/ผู้ประสานงาน | สรุปรายงานและทำงานร่วมกัน | FDH AI Report, ศูนย์ประสานงาน, คู่มือ |
| ผู้ติดตั้งระบบ | ติดตั้ง อัปเดต สำรองข้อมูล และ rollback | คู่มือติดตั้งและเอกสารใน `deploy/` |

สิทธิ์จริงขึ้นกับ `is_admin`, กลุ่มผู้ใช้ และ `menu_permissions` ของผู้ใช้ หากเปิดเมนูแล้วพบข้อความว่าไม่มีสิทธิ์ ให้ผู้ดูแลเพิ่มสิทธิ์ที่กลุ่มก่อน ไม่ควรใช้บัญชีผู้ดูแลร่วมกัน

## 3. ผู้ดูแลระบบ

### งานที่รับผิดชอบ

- สร้างผู้ใช้ ปิดบัญชีผู้ที่ย้ายงาน และกำหนดกลุ่ม
- กำหนดสิทธิ์เมนูตามตารางด้านบน
- ตั้งค่าโรงพยาบาล ฐานข้อมูล และระบบ AI
- ตรวจสอบ audit log และจัดการเหตุผิดปกติ
- ตรวจรุ่นใหม่ที่ **ตั้งค่าระบบ → อัปเดตระบบ** และกดยืนยันหลังตรวจรายการเปลี่ยนแปลง

### ขั้นตอนเริ่มต้นโรงพยาบาลใหม่

1. สร้างกลุ่มตามหน้าที่ แล้วกำหนดเมนูให้น้อยที่สุดเท่าที่จำเป็น
2. สร้างบัญชีผู้ใช้และบังคับให้เปลี่ยนรหัสผ่านเมื่อเริ่มใช้งาน
3. เปิด **ตั้งค่า → ฐานข้อมูล HOSxP** เลือก MySQL/MariaDB หรือ PostgreSQL
4. ทดสอบการเชื่อมต่อและกดบันทึก จากนั้นรีสตาร์ต backend หากระบบแจ้งให้ทำ
5. ให้ผู้ดูแล HOSxP ตรวจสอบ VN/AN ตัวอย่าง แล้วให้เจ้าหน้าที่ตรวจรายการจริง

### ข้อควบคุม

- ไม่ใส่รหัสผ่านหรือไฟล์ `.secrets` ลง GitHub
- ใช้บัญชีฐานข้อมูลแบบ read-only สำหรับ HOSxP เมื่อทำได้
- สำรองฐานข้อมูลแอปก่อนเปลี่ยนโครงสร้างหรืออัปเดตใหญ่
- เปลี่ยนรหัสผ่านเมื่อมีบุคลากรพ้นหน้าที่
- ระหว่างอัปเดตให้รอแถบสถานะจน health check ผ่าน หากการเชื่อมต่อหลุด หน้าเดิมจะกลับมาติดตามงานให้อัตโนมัติ

## 4. ผู้ดูแล HOSxP/IT

### ข้อมูลที่ต้องเตรียม

- HCODE และชื่อโรงพยาบาล
- IP/hostname, port, database และ schema ของ HOSxP
- บัญชีอ่านข้อมูล HOSxP และสิทธิ์ที่จำเป็น
- ฐานข้อมูล REP/STM ของแอป (โดยทั่วไปยังเป็น MySQL/MariaDB)
- รหัสมาตรฐานที่ใช้จริง: diagnosis, ADP, icode, tmcode, lab, drug, สิทธิ์ และหน่วยบริการ
- URL ของ Local AI หากเปิดใช้ เช่น `http://10.10.20.119:11434` และชื่อโมเดล
- VN/AN ตัวอย่างของ OPD, IPD, ANC, กองทุนเฉพาะ และรายการที่มี REP/STM/INV

### MySQL/MariaDB และ PostgreSQL

ระบบรองรับการอ่าน HOSxP ทั้งสองแบบ แต่ PostgreSQL เป็นการเชื่อมต่อแบบอ่านอย่างเดียว การเขียนข้อมูลเติมอัตโนมัติหรือสร้างตารางใน HOSxP จะถูกปิดไว้ ฐานข้อมูล REP/STM และฐานข้อมูลของแอปยังต้องใช้ตามที่ระบบกำหนดแยกต่างหาก

หลังเปลี่ยน server หรือบัญชี ให้กรอกรหัสผ่านใหม่ ทดสอบ connection และทดสอบอ่านข้อมูลจริงอย่างน้อยหนึ่ง VN/AN ห้ามตั้งค่า backup แบบ `FDH_BACKUP_HOSXP=1` กับ PostgreSQL จนกว่าจะมีวิธี backup ที่รองรับจริง

รายละเอียดตัวแปรและขั้นตอนอยู่ที่ [คู่มือฐานข้อมูลโรงพยาบาล](../deploy/HOSPITAL_DATABASE.md)

### ตรวจสอบเมื่อระบบมีปัญหา

1. ตรวจ `/api/ready` และ log ของ backend/PM2
2. ตรวจ firewall, port, SSL และสิทธิ์ฐานข้อมูล
3. ทดสอบ query ด้วยผู้ใช้เดียวกับที่ตั้งค่าในระบบ
4. ตรวจ schema และชื่อคอลัมน์ของ HOSxP รุ่นนั้น โดยเฉพาะ ADP, lab, drug และ procedure
5. บันทึกตัวอย่าง VN/AN ที่พบปัญหาเพื่อส่งต่อให้ผู้ดูแลระบบ

## 5. เจ้าหน้าที่เวชระเบียนและ OPD

### งานประจำวัน

1. เข้า **รายการ OPD** เลือกช่วงวันที่และดึงข้อมูล
2. ตรวจ HN/VN, สิทธิ์, diagnosis, วันที่รับบริการ และรหัส ADP/หัตถการ
3. เปิด **กองทุนเฉพาะ** ตรวจรายการ ANC, Palliative, Telemedicine และกองทุนอื่นตามที่โรงพยาบาลใช้
4. แก้ข้อมูลที่ผิดใน HOSxP แล้วดึงข้อมูลใหม่
5. ใช้ **ตรวจสอบก่อนส่ง** ก่อนส่ง FDH และบันทึกรายการที่ต้องติดตาม

### Auto Complete

ปุ่มเติมข้อมูลอัตโนมัติใช้ช่วยกรอกข้อมูลที่ตรงกับบริการที่มีหลักฐานอยู่แล้วเท่านั้น เช่น ANC ตรวจฟันและ ANC ขัดทำความสะอาดฟัน ต้องตรวจ diagnosis, ADP, รหัสทันตกรรม และบันทึกการให้บริการก่อนกด หากเป็น PostgreSQL ปุ่มที่ต้องเขียนกลับ HOSxP อาจใช้งานไม่ได้ ให้แก้ที่ HOSxP ด้วยผู้มีสิทธิ์แทน และตรวจ audit ทุกครั้ง

## 6. เจ้าหน้าที่ IPD

1. เปิด **รายการ IPD** ตรวจ AN, วันรับ-จำหน่าย, diagnosis และ procedure
2. ตรวจความครบถ้วนของข้อมูลก่อนส่งออกที่ **ส่งออก IPD**
3. ใช้ **Monitor IPD Claim** ติดตามสถานะเคลมและรายการค้าง
4. แก้ข้อมูลต้นทางใน HOSxP แล้วดึงและตรวจซ้ำ
5. ส่งต่อรายการผิดปกติพร้อม AN และช่วงวันที่ให้ทีมประกัน

## 7. งานประกันและเคลม

### ก่อนส่ง

- ตรวจ **FDH/e-Claim → ตรวจสอบก่อนส่ง** และแก้รายการเตือนให้หมด
- ตรวจเลขบัตร, HN/VN/AN, สิทธิ์, diagnosis, ADP และยอดเงิน
- ตรวจรหัสเตือนที่กำหนดให้ครบตามรูปแบบ เช่น รหัส S ต้องมีห้าหลัก
- ส่งเฉพาะรายการที่ผ่านการตรวจและมีผู้รับผิดชอบชัดเจน

### หลังส่งและนำเข้าผล

1. ตรวจสถานะใน **สถานะนำเข้า/ตรวจสอบ**
2. นำเข้า REP/STM/INV ที่ได้จากหน่วยงานที่เกี่ยวข้อง
3. ใช้เลข VN/AN, Tran ID, เลข REP หรือ Statement เพื่อจับคู่
4. ตรวจรายการตีกลับและ C/Deny แล้วส่งข้อแก้ไขกลับไปยัง OPD/IPD
5. ปิดสิทธิ์หรือดำเนินการ NHSO ตามรอบงานของโรงพยาบาล

หากพบ REP แต่ไม่พบ STM/INV ให้ตรวจรอบไฟล์ ช่วงวันที่ และรหัสอ้างอิงก่อนสรุปว่าไม่มีข้อมูล อย่าลบไฟล์นำเข้าเดิมจนกว่าจะตรวจสอบและสำรองแล้ว

## 8. การเงินและลูกหนี้

- ใช้ **การเงิน/บัญชี** ตรวจยอดที่เรียกเก็บและยอดที่ได้รับ
- ใช้ **ลูกหนี้**, **UUC1** และ **UC นอก CUP** ติดตามรายการค้างและรายการที่ควรเรียกเก็บ
- ใช้ **รายงาน REP ประจำวัน** กระทบยอดรายวันกับ REP/STM/INV
- ใช้ **โอกาสรายได้** เพื่อค้นหารายการที่ควรทบทวน โดยให้หัวหน้างานอนุมัติก่อนแก้ข้อมูล
- ส่งผลต่างกลับทีมประกันพร้อมเลขอ้างอิงและจำนวนเงิน ไม่ส่งต่อเป็นข้อความสั้น ๆ ที่ไม่มีหลักฐาน

## 9. หัวหน้างานและผู้บริหาร

ใช้ **Dashboard**, **รายงานโรงพยาบาล**, **ภาพรวมสิทธิ์** และ **วิเคราะห์กองทุน** เพื่อดูจำนวนรายการผ่าน/ค้าง/ตีกลับ ยอดเงิน และแนวโน้มตามช่วงเวลา การอนุมัติแก้ข้อมูลควรอ้างอิงรายงานและรายการต้นทาง ไม่ควรให้ผู้บริหารใช้บัญชีเพื่อแก้ข้อมูลรายคน

## 10. ตารางกองทุนที่ควรตรวจเป็นพิเศษ

| งาน | จุดตรวจหลัก |
|---|---|
| Palliative | Z51.5, Z71.8 เมื่อเข้าเกณฑ์, ADP 30001/Cons01/Eva001 และบริการเยี่ยมบ้าน |
| ANC | Z34/Z35 และ ADP 30010–30013 ตามบริการจริง |
| ANC ตรวจฟัน | ADP 30008, รหัสทันตกรรม และรหัส ICD-9 ที่เกี่ยวข้อง |
| ANC ขัดทำความสะอาดฟัน | ADP 30009 และรหัส scaling/polishing พร้อมหลักฐานบริการ |
| Telemedicine | รหัสบริการและช่องทางส่งออก TELMED ให้ตรงกับที่ตั้งค่า |
| ข้อเข่า | อายุ เกณฑ์โรค M17/U57.53 หัตถการ และจำนวนครั้งตามเงื่อนไข |

รายการด้านบนเป็นจุดตรวจเบื้องต้น ต้องยึดประกาศและ mapping ของกองทุนในช่วงเวลานั้นเสมอ

## 11. ผู้ติดตั้งและผู้ดูแลการ deploy

ให้ทำตาม [คู่มือติดตั้ง Production](../deploy/README.md) โดยตรวจ Node.js, Nginx, PM2, `.env`, สิทธิ์ไฟล์, backup, health check และ rollback ก่อนเปิดให้ใช้งานจริง หลัง deploy ให้ทดสอบ login, OPD, IPD, การนำเข้า REP/STM/INV, PostgreSQL (ถ้ามี) และ Local AI จากเครือข่ายของโรงพยาบาล

เอกสารนี้ใช้คู่กับ [Quick Start](../QUICK_START.md) และควรบันทึกค่าของแต่ละโรงพยาบาลไว้ในเอกสารภายในที่ไม่เผยแพร่รหัสผ่าน

## 12. แก้ปัญหาเบื้องต้น

| อาการ | ตรวจสอบก่อนส่งต่อ |
|---|---|
| Login ไม่ได้ | backend พร้อมหรือไม่, URL ถูกต้อง, บัญชีถูกปิดหรือไม่, เวลาเครื่อง และ log authentication |
| เห็นเมนูไม่ครบ | กลุ่มผู้ใช้และ `menu_permissions` |
| Internal Server Error | `/api/ready`, log backend, ช่วงวันที่, การเชื่อมต่อ HOSxP และชื่อคอลัมน์ |
| PostgreSQL อ่านไม่ได้ | host/port/schema/SSL/สิทธิ์ และ query ที่ใช้จริง |
| Auto Complete ไม่เติม | หลักฐานบริการ, mapping code, สิทธิ์เขียน และข้อจำกัด PostgreSQL |
| REP/STM/INV ไม่จับคู่ | VN/AN/Tran ID, รอบไฟล์, วันที่ และรูปแบบไฟล์ |
| AI ใช้ไม่ได้ | `OLLAMA_BASE_URL`, การเข้าถึง `10.10.20.119:11434`, ชื่อโมเดล `qwen3:4b-instruct` และ firewall |

ทุก ticket ควรแนบเวลาเกิดเหตุ, ชื่อเมนู, ผู้ใช้, VN/AN/Tran ID ที่เกี่ยวข้อง และปกปิดเลขบัตรประชาชนกับรหัสผ่าน
